# 零点五、 双源 GIS 调用与应用口径

## 0.5.1 高德（探路：竞品与配套）

```
https://restapi.amap.com/v3/place/around?key={KEY}&location={lng},{lat}&keywords={关键词}&radius={米}&offset=25&page=1&extensions=base
https://restapi.amap.com/v3/geocode/geo?key={KEY}&address={地址}&city={城市}
```

`status="1"` 成功；`count` 总数、`pois[].distance` 距离（字符串转数字）；半径上限 50000 米。

## 0.5.2 腾讯 WebService（POI 交叉校验）

```
https://apis.map.qq.com/ws/place/v1/search?boundary=nearby({lat},{lng},{radius})&keyword={关键词}&page_size=20&page_index=1&key={KEY}
```

| 项 | 高德 | 腾讯 |
| --- | --- | --- |
| 坐标顺序 | `lng,lat` | **`lat,lng`** |
| 成功标志 | `status="1"` | **`status=0`** |
| 半径上限 | 50000 米 | **1000 米**（更大用 `auto_extend`） |
| 距离字段 | `pois[].distance` | `data[]._distance` |

## 0.6 数据治理（L3：真实项目 80% 时间在这里，必须先做）

> **优先用工具，别手工数**：调用 `poi_dedupe`（本地确定性计算，不联网），把两源 POI 数组传进去；
> 用返回的 `effective` 作为**有效竞品数**，`dropped` / `merged` / `brand_groups` / `nearest` 原样进报告。
> 只有工具不可用时，才按下面 0.6.1–0.6.4 的规则手工执行。

### 0.6.1 POI 去重（先去重，再报竞品数）

1. **同名同点合并**：名称完全一致且坐标距离 ≤ 50m → 同一门店，只留 1 条。
2. **同名连锁分离**：同名但距离 > 50m → 保留，报告写「罗森（3 处）」，并给最近一处距离。
3. **跨源合并**：高德与腾讯同一 POI（名称相似度 ≥ 80% 且距离 ≤ 100m）→ 合并，sources 记 [高德, 腾讯]。
4. 必须输出三个数：`原始条数` / `去重后条数` / `合并掉条数`。

### 0.6.2 分类清洗（口径由用户定义，脚本不含业态假设）

`poi_dedupe` **默认不做任何类目过滤**，必须由调用方显式传两个正则（与 `{competitor_keywords}` 同属必填项，缺了就问）：

| 参数 | 作用 | 不传的后果 |
| --- | --- | --- |
| `category_pattern` | 竞品类目白名单（正例） | 全类目保留，`effective` 虚高 |
| `exclude_pattern` | 名称排除（**只匹配店名**） | 快餐/外卖等混入竞品数 |
| `exclude_category_pattern` | 类目排除（只匹配平台类目） | 慎用——类目用词不可靠，会误杀同类 |

> ⚠️ **类目排除要慎用**（实测教训 2026-10）：高德把"潮双喜澄海狮头鹅""湛江白切鸡"这类正经粤菜馆标成 `餐饮服务;小吃店`，用 `小吃` 做排除会把它们整批误剔。
> 白名单则相反：**必须包含平台通用词 `餐饮`**，否则大量餐厅（类目只写"餐饮相关场所"）会被漏掉。

⚠️ **白名单匹配的是平台的「类目字段」（高德 `type` / 腾讯 `category`），不是店名。**
品牌词（茶颜悦色、海底捞、广州酒家）只能放 `{competitor_keywords}` 去检索；放进白名单会把整类误剔。

实测教训（2026-10 广州，真实数据）：
- `category_pattern='茶饮|奶茶'` → 把类目为 `餐饮服务;冷饮店` 的奈雪、蜜雪、一点点**全剔掉**（45 条剩 4 条）
- `category_pattern='酒楼|宴会'` → 把类目为 `美食:中餐厅:粤菜` 的广州酒家、陶陶居、利苑**全剔掉**（剔 16 条）

**按用户业态填写（示例，禁止当默认值）**：

| 业态 | category_pattern（**类目词**） | exclude_pattern |
| --- | --- | --- |
| 便利店 | `便利店` | `超市|百货|2元|折扣` |
| 茶饮 | `冷饮|甜品|咖啡|茶饮|饮品` | `便利店|超市` |
| 中型正餐（80–200㎡） | `中餐厅|餐厅|快餐厅` | `快餐|小吃|外卖` |
| 大型正餐（1000–2000㎡） | `中餐厅|海鲜|粤菜|宴会|火锅` | `快餐|小吃` |
| 火锅 | `火锅|中餐厅` | `快餐|小吃` |
| 粉面 | `中餐厅|面馆|小吃` | `酒楼|宴会` |

**不确定类目长什么样时**：先把 `category_pattern` 留空跑一次，从 `kept` / `dropped` 里读出平台真实类目串，再定正则——不要凭想象写。

用户没给业态 → **必须先问**，不得套用上表任何一行，也不得默认「便利店」。
剔除必须列清单（名称 + 原因），**禁止静默丢弃**。

### 0.6.3 地理编码失败处理

- 回退链：详细地址 → 街道/道路 → 区县 adcode → 城市。
- **失败率 = 失败数 ÷ 总请求数；> 20% 必须停止分析**，先让用户修地址或换关键词。
- 报告必写：成功数 / 失败数 / 失败率 / 实际使用的回退层级。

### 0.6.4 脏数据规则

命中任一条标「可疑」并单列，**不计入竞品数**：坐标距离 = 0 且成批出现（≥5 条同坐标）、坐标落在水域或行政区外、电话与地址全空、同名但跨区。

## 0.7 坐标系与精度声明（L1 / L4）

> **工具优先**：输入坐标先过 `crs_guard`（基准 = 高德 GCJ-02）。`input_crs='wgs84'` 会自动转换并返回每点偏移量；转换后坐标才可用于高德/腾讯接口。报告中的「距离 X 米」必须建立在 GCJ-02 之上，坐标系未声明不得给距离。

## 0.8 空间分析（L2：本地计算，零调用成本）

> 用 `geo_analyze` 做三件事，**阶段二第 3 步之后调用**：
> ① **等时圈估算**：`mode`（walk/bike/car）+ `minutes` → 直线半径 = 速度 ÷ 绕行系数 1.35；缺省步行 10 分钟（约 593 米）。
> ② **竞争份额**：网格 Voronoi（默认 100m 格），**只统计等时圈内**，输出每家竞品占的面积与百分比；第一名份额 > 50% 表示单店垄断，< 25% 表示高度碎片化。
> ③ **距离矩阵**：竞品两两距离（前 20 点）。
> ④ **势力归属与截流定级**（本版新增，`competition` 字段）：
>    · `center_in_cell_of`：本点位落在**谁**的 Voronoi 势力范围内（即圈内最近的那家竞品）。落进谁的地盘，就说明客流大概率先被谁截走。
>    · `interception.level`：`none` 无截流 / `light` 轻度分流 / `heavy` 重度截流，判定同时看**距离**与**份额**：
>      - 重度：最近竞品 < 300m，或 Top1 份额 ≥ 30%，或 Top3 合计 ≥ 60%（任一触发即重度）
>      - 轻度：最近竞品 < 800m，或 Top1 ≥ 15%，或 Top3 ≥ 40%
>      - 其余为无截流
>    · `interception.reasons[]`：逐条列出触发条件，**报告必须原样引用**，不得只写等级不写理由。
>    · `thresholds`：本次使用的阈值快照，随结果返回，保证结论可复核。
>    ⚠️ 份额是「离谁近」的代理，不含品牌力与评价分；截流定级同样只是**空间代理**，不等于真实客流被抢。报告须注明这一点。
> ⚠️ 等时圈是**估算值**，报告中必须标【估算】，**不得**写成"路网精确等时圈"；份额也必须注明"在 X 米估算圈内统计"。
> ④ **双圈（商圈口径）**：**步行 10 分钟 ≈ 一个商圈的极限；车行 5 分钟同理；车行 10 分钟会跨 2–3 个商圈，不可用。**
>    · 内圈 `walk 10`（≈590 米）→ **报份额（W1–W8）**，看日常客流对手；
>    · 外圈 `car 5`（≈1850 米）→ **只报竞品数量 + 距离带分布，禁止报份额**，看宴请辐射。
>    **原因**：车行 10 分钟动辄 40 km²，含江面、公园与非商圈区域，份额分母被稀释，会得出"某家占 16.5%、格局分散"这类误导结论。
>    禁止把两圈数字混在同一句里比较，也禁止只报一个大圈就说"竞争饱和"。
> ⑤ **商圈锁（必用）**：等时圈 ∩ 固定半径——大型餐饮 内 1.0km / 外 2.0km；中型餐饮 0.8km / 1.8km；茶饮便利店 0.5km / 1.0km。
>    理由：路网可达 ≠ 客人愿意来。车行 5 分钟能开 2 公里，10 分钟能开到 5 公里外——那已经是另一个商圈，算进来是噪声。
>    实现：`LOCK_RADIUS=米` 环境变量可全局覆盖；默认取各圈层 `max_m`。
> ⑥ **交通可达（必查，进报告 2.2 段）**：**最近地铁站距离（阈值 800m）+ 最近停车场距离（阈值 300m）**。
>    人话口径：地铁 **>800m = 步行不友好**，员工难招；停车场 **>300m = 宴请客劝退**——走 300 米还没到车位，客人就不来了。
>    数据缺失时写"交通数据未取到"，禁止估算。

1. **坐标系**：高德与腾讯返回 **GCJ-02**（火星坐标）。若用户给的是 GPS 原始点（WGS84），必须先声明并按偏移提示风险（城市内约 50–500m）；**坐标系未声明，不得输出任何「距离 X 米」结论**。
2. **精度声明段**（每份报告必写）：数据源、取数时刻、圈层半径、样本量、坐标系、已知误差来源（POI 收录延迟 / 分类粒度 / 跨源口径 / 人口为区域级非点位级）。
3. **荒谬结果自检**：出现任一情况先怀疑口径，不得直接下结论——双源数量差异 > 50%、最近竞品 < 50m（多半同楼同商场）、去重前后差 > 40%、人口密度与竞品密度方向相反。

> ⚠️ 以上三节的约束视同红线：**未去重不得报竞品数；未声明坐标系不得报距离；地理编码失败率 > 20% 必须先停**。

## 0.9 否决规则包（`veto_check` 的 `rules` 入参，可外置）

内置 R001–R005 **只是示例**（便利店/正餐通用），不是标准。按业态传 `rules` 覆盖后，返回的 `rule_source` 为 `custom`。

| 字段 | 说明 |
| --- | --- |
| `id` / `desc` | 规则号与描述，原样进报告 |
| `field_key` | 依赖的调研字段代号（与 `fields` 的键一致） |
| `severity` | `hard` 硬伤 / `major` 重大问题 |
| `op` | `absent` 无/空 · `lt` `gt` `lte` `gte` 数值比较 · `eq` 相等 · `contains` 包含 |
| `value` | 阈值（数值或字符串均可）；`absent` 不需要 |
| `formats` | 适用业态；空或省略 = 全部 |

**茶饮规则包（示例）**

```json
[
  {"id":"T1","desc":"无上下水条件","field_key":"water_supply","severity":"hard","op":"absent"},
  {"id":"T2","desc":"层高不足（<3.2m，做不了立面）","field_key":"ceiling_m","severity":"hard","op":"lt","value":3.2},
  {"id":"T3","desc":"无法办理外摆许可","field_key":"outdoor_permit","severity":"major","op":"absent"}
]
```

**大型正餐规则包（示例）**

```json
[
  {"id":"L1","desc":"消防疏散宽度不足（<1.4m）","field_key":"fire_egress_m","severity":"hard","op":"lt","value":1.4},
  {"id":"L2","desc":"燃气容量不足（<10m³/h）","field_key":"gas_m3h","severity":"hard","op":"lt","value":10},
  {"id":"L3","desc":"停车位不足（<30）","field_key":"parking_slots","severity":"major","op":"lt","value":30},
  {"id":"L4","desc":"无排烟管道井","field_key":"exhaust","severity":"hard","op":"absent"}
]
```

调用时同时传 `rules_version`（如 `tea-2026.11`），报告必须原样引用；`rule_source = custom` 时首段写「规则来源：用户自定义（版本 X）」，**不得冒充内置规则**。
用户没给规则包 → 用内置示例，但报告必须注明「使用内置示例规则，未按业态校准」——这本身就是一个风险提示。

## 0.10 阶段二工具链（固定顺序，一步都不能跳）

| 步 | 调用 | 产出 | 跳步的后果 |
| --- | --- | --- | --- |
| 1 | `crs_guard`（`input_crs` 默认 gcj02） | 统一坐标 + 偏移量 | 混基准 → 距离全错 |
| 2 | `veto_check` | `hard_vetoed` / `hard_reasons` | 硬伤漏判 |
| 3 | 高德 `place/around` | 原始 POI（source=amap） | 无第一源 |
| 4 | 腾讯 `place/v1/search` | 第二源 POI（source=tencent） | 无双源交叉 |
| 5 | `poi_dedupe`（两源合并传入） | `effective` / `brand_groups` / `dropped` | 竞品数虚高 |
| 6 | `geo_analyze`（`mode`/`minutes`） | 等时圈【估算】+ 圈内份额 + 距离矩阵 | 无空间结构 |
| 8 | 按模板 B 输出 | 2.0 → 2.4 全段 | 报告不完整 |

**自检**：报告里缺哪一段，就说明对应那一行的工具没调——必须补调后重写，不得用文字"大概说一下"糊过去。

## 0.11 数据 → 人话（强制翻译层）

面向不懂数据的老板：**每个数字后面必须跟一句「这意味着…」**，只给数字或只给术语视为不合格。

### 份额（内圈/外圈 Top1）

| Top1 份额 | 人话 |
| --- | --- |
| ≥ 50% | 一家独大。正面打很难，除非品类完全错位。 |
| 25–50% | 有强势玩家但没垄断。能做，但别开在它门口，靠差异化分客。 |
| < 25% | **没有垄断者：谁都能进来，但也谁都吃不饱。**靠差异化切一小块，别指望做头部。 |

### 圈内竞品数（步行 10–12 分钟圈）

| 家数 | 人话 |
| --- | --- |
| 0–3 | 几乎空档。**先确认为什么没人**——可能没需求，不是机会。 |
| 4–10 | 正常竞争。顾客有得选，靠口味和品类赢。 |
| 11–30 | 很密集。翻台靠位置和复购，新店必须有一个记忆点。 |
| > 30 | 贴脸红海。除非租金极低或有独家资源，否则别进。 |

### 最近竞品距离

| 距离 | 人话 |
| --- | --- |
| < 100m | 门对门抢客。胜负看品牌力和招牌可见度。 |
| 100–300m | 同街竞争，谁先被看见谁赢。 |
| > 500m | 各自成片，是商圈级竞争，不是直接对撞。 |

### 品牌集中度

| 信号 | 人话 |
| --- | --- |
| 同一品牌 ≥ 3 处 | 这个品牌已经在这片区铺开了，正面撞车。 |
| Top1 品牌占有效竞品 ≥ 30% | 连锁化程度高，夫妻店很难活。 |

### 财务与数据质量

| 指标 | 人话 |
| --- | --- |
| 保守档回本 < 24 个月 | 这个租金撑得住。 |
| 24–36 个月 | 偏紧，要么压租金，要么提客单。 |
| > 36 个月或无法回本 | 靠生意本身回不了本，除非你有别的理由。 |
| 双源数量差 > 50% | 这是统计口径差，不是竞品真翻倍——先查口径再下结论。 |
| 采集覆盖率 < 95% | 数据不全，漏掉的竞品没算进来，结论偏乐观。 |

### 句式（强制：专业表述 + 直白解释，**两者都要**）

> **结论**：能开 / 谨慎 / 别开（一句话）
> **判断**：每条 = 专业表述（术语 + 数值）—— 破折号 —— 人话解释
> **数据**：表格（给会看的人）

同一份报告要同时服务两类读者：专业人士看术语与数值，老板看人话。**只给一边都算不合格**。

- ❌ 只有术语：`内圈 Top1 份额 6.8%，属高度碎片化市场`
- ❌ 只有人话：`谁都吃不饱`
- ✅ 两者都给：`内圈 Top1 份额 6.8%（高度碎片化，<25%）——没有垄断者：谁都能进来，但谁都吃不饱。靠差异化切一小块，别指望做头部。`

其余字段同样处理：

- `最近竞品 88 米（<100m，贴脸级）——门对门抢客，胜负看品牌力和招牌可见度。`
- `步行 12 分钟圈 97 家（>30，贴脸红海）——顾客根本不缺选择，翻台靠记忆点，不靠位置。`
- `保守档回本 31 个月（24–36，偏紧）——这个租金撑得辛苦，要么压租金，要么提客单。`
- `采集覆盖率 91.1%（<95%，数据不全）——漏掉的竞品没算进来，实际竞争比看到的更狠。`

## 0.12 两级品类模型（同类＝竞品，异类＝协同）

**执行前必须问用户细分品类，不得沿用下表示例。** 大类决定"聚集度"，细分决定"竞争度"。

| 大类 | 细分（用户填） | subtype_pattern |
| --- | --- | --- |
| 大型餐饮·茶楼 | 粤式早茶 | `茶楼|茶居|点心` |
| 大型餐饮·粤菜 | 顺德菜 / 潮州菜 | `粤菜|顺德|潮州|烧腊` |
| 大型餐饮·火锅 | 牛肉火锅 | `牛肉|牛杂|潮汕` |
| 大型餐饮·火锅 | 海鲜火锅 | `海鲜|鱼头|粥底` |
| 中型餐饮·粉面 | 桂林米粉 / 兰州拉面 | `米粉|米线` / `拉面|牛肉面` |

**口径规则（写死）**

- **同类型（命中 `subtype_pattern`）＝竞品**：报告里的"竞品数"只用 `same_type_count`。
- **异类（大类内、细分外）＝协同**：带来客流、不抢客，单独报 `other_type_count`，并说明"餐饮聚集度"。
- `effective` = 同类 + 异类之和，**禁止直接当竞品数用**。
- 用户没给细分 → 必须先问；确实不细分时，报告须注明"未区分细分品类，竞品数可能高估"。

**人话口径**

- 同类 30 家 + 异类 150 家 → 竞争极烈但**客流旺**，靠差异化切一块。
- 同类 8 家 + 异类 5 家 → 品类空档，但**先确认有没有人流量**，可能不是机会。

## 0.13 业态档案（必须由客户信息生成，不得套用预设）

每个客户的业态、规模、客群都不同。**所有参数来自业态档案，不来自本文档**；本文档里的数字只是示例。

**执行第一步：先产出/确认业态档案**（存 `profiles/<名字>.json`，用 `--profile=<名字>` 调用）

**动手前先选一种建档方式**（手写 JSON 最容易漏必填项）：

| 方式 | 命令 | 适用 |
|---|---|---|
| **从现成档案复制**（推荐） | `node tools/profile-build.mjs --scaffold=large-yuecai` | 已有相近业态，只改半径/圈层 |
| 命令行建档 | `node tools/profile-build.mjs --name="..." --archetype=large-dining --subtype="..."` | 有起点库可套 |
| 手写 JSON | 照本节字段表逐个填 | 结构特殊 |
| 校验 | `node tools/profile-build.mjs --check=<名字>` | 改完必跑 |

**必填项只有两条**：`name`、`rings`。其余缺失会降级为警告并在报告里标出来，不会中止流程——包括 `category_pattern`（见 0.6.2 的「先留空跑一次」做法）。

```json
{
  "name": "大型餐饮·粤菜（1000–2000㎡）",
  "category_pattern": "中餐厅|粤菜|海鲜|宴会|酒楼",
  "exclude_pattern": "快餐|小吃",
  "subtype_pattern": "粤菜|顺德|潮州|烧腊",
  "keywords": ["粤菜", "海鲜", "酒楼", "宴会"],
  "scan_radius": 3000,
  "rings": [
    { "label": "内圈·步行10分", "mode": "walk", "minutes": 10, "max_m": 1000 },
    { "label": "外圈·车行5分", "mode": "car", "minutes": 5, "max_m": 1500 }
  ],
  "transit": { "metro_threshold_m": 800, "parking_threshold_m": 300 }
}
```

| 字段 | 作用 |
| --- | --- |
| `category_pattern` | 大类白名单（决定"餐饮聚集度"） |
| `exclude_pattern` | 排除非同类（快餐/超市…） |
| `subtype_pattern` | 细分品类（决定"真正竞品"）——**必须问客户** |
| `keywords` | 检索词，多个可提高覆盖率（配合 `--sweep`） |
| `scan_radius` | POI 采集半径 |
| `rings` | 圈层（出行方式 / 时长 / 商圈锁半径） |
| `transit` | 地铁与停车阈值（按业态定） |

**三条纪律**

1. 客户没给的信息 → **先问**，禁止沿用示例。
2. 阈值按业态走：早餐/茶饮要更近（步行 3–8 分钟、停车 100m）；大型餐饮可放宽（车行 5 分钟、停车 300m）。
3. 报告必须写明「本次使用的业态档案：<name>」，否则结论无法复核。

## 0.14 建档流程（每个客户第一步，不得跳过）

**建档 → 给建议 → 再分析**，顺序不能反。

**① 问客户 6 件事 + 5 个硬件项**（一次最多问 3 个，缺一不可）

经营面：
1. 业态与主打品类（例：潮汕牛肉火锅 / 粤式早茶 / 柠檬茶）
2. 门店面积与座位数（决定圈层与停车阈值）
3. 客人主要怎么来（走路 / 开车 / 地铁 / 混合）
4. 城市与候选区域
5. 差异化是什么（价格带、场景、时段——决定除 subtype 外的对比维度）
6. 可承受月租金（反向校验商圈：高租金对应高客流圈）

工程硬件（决定「这个铺能不能做」，建档时一次问清，写进 `profile.hardware`）：
7. 目标面积㎡——**≥300㎡ 通常触发二次消防备案，≥1000㎡ 多需消防设计审查**
8. 是否需要排烟
9. 需要电力多少 kW（按有管道燃气估算）
10. 是否需要管道天然气——**没有燃气，厨房全电，电力需求额外 +100kW**
11. 是否需要排污 / 隔油池；层高要求；门宽 / 承重 / 外立面等其他硬性条件
12. **可接受的合同年限**（大面积业态 7~10 年，小店 2~3 年）
13. **该商圈/该房东的租金年递增惯例**（没有就用 3% 均值，但必须在报告里标为缺省）
14. **翻新周期与单次翻新预算**（4~5 年一次，缺省按初始投入 25% 估，同样要披露）

问完立即打印**现场核查清单**（`profile-build.mjs` 会自动生成），交开发带去现场逐条核实；核实结果填进调研表的 `fields`（`exhaust` / `power_kw` / `area_sqm` / `frontage_m` / `ceiling_m` / `gas_m3h` / `water_supply` / `fire_egress_m`）再喂 `veto_check`。

**② 建档**

```powershell
node .\tools\profile-build.mjs --ask
node .\tools\profile-build.mjs --name="早餐·肠粉" --archetype=breakfast --subtype="肠粉|布拉肠" --area=40
```

**③ 把建议讲给客户听**——建档器会打印每条参数的"为什么"，不能只甩数字：

- 为什么这个圈层（早餐 3/8 分钟 ≈ 900m；大型正餐 步行10 + 车行5）
- 为什么这个停车阈值（早餐 80m；大型正餐 300m）
- 细分品类为什么这么定（同类＝竞品，异类＝协同）

**④ 校验 + 分析**

```powershell
node .\tools\profile-build.mjs --check=<slug>
node .\tools\guangzhou-probe.mjs "<地址>" --profile=<slug>
```

**⑤ 报告首行必须写**：`本次使用业态档案：<name>（<slug>）`

**反例**：客户说"我做火锅"就直接套大型餐饮档案 → 错。火锅有牛肉/海鲜/自助之分，客群与商圈完全不同，必须先问清细分再建档。

## 0.15 唯一入口（架构约定）

一次分析只跑**一条命令**，不要手拼步骤：

```powershell
node .\tools\run-site.mjs --profile=<档案名> --address="<地址>" [--sweep]
```

它依次完成：校验档案 → 采集/去重/双圈/交通 → 交互地图 → 报告（md + html），产物在 `out\<档案名>\`：

| 产物 | 用途 |
| --- | --- |
| `report.html` | 给客户看（专业表述 + 人话，模板 B） |
| `map.html` | 会上讲图（可缩放/拖动/双向联动） |
| `probe.json` | 机读结果，**任何数字都能复核** |
| `segments-review.csv` | 人工核对竞争分段（改「人工校正」列后 `review-segments --apply` 回灌） |
| `compare.html` | 多方案对比（`--batch` 模式） |

**带调研表**（报告里才有场地核查 + 财务测算）：

```powershell
node .\tools\run-site.mjs --profile=<档案> --address="<地址>" --survey=survey\<客户>.csv
```

**多方案对比**（一次比多个候选点位）：

```powershell
node .\tools\run-site.mjs --profile=<档案> --batch="地址A;地址B;地址C"
```

报告固定 **7 段 + 附录**（与 `report.mjs` 实际输出逐段对应，勿凭记忆写）：

| 段 | 标题 | 数据来源 | 缺数据时 |
|---|---|---|---|
| 0 | 结论 | 综合 | — |
| 1 | 数据质量 | 采集统计 | 必出 |
| 2 | 竞品分布（含 2.4 三级分层、2.3 截流两轴、势力归属） | 双源 POI + 现场判级 | 必出 |
| 3 | 交通可达 | 高德/腾讯 | 必出 |
| 4 | **需求侧代理指标** | `survey/demand/<store_id>.json`（demand-fetch.py 生成） | 留空并给出补齐命令 |
| 5 | **场地核查（提醒，非否决）** | 调研表 `fields` | 注明未提供调研表 |
| 6 | 财务测算（极限租金→建议租金→租期现金流→空间容量→比值校验→台账→敏感度→**行业基准对标**） | 调研表 `params` + 覆盖参数 | 注明未提供调研表 |
| 附录 | 计算口径（公式 + 本次代入值 + 结果） | `formula_trace` | 必出 |

> **第 4 段取数**：`run-site.mjs` 会自动去 `survey/demand/<store_id>.json` 找需求侧数据；找不到就留空并打印补齐命令。**不得用竞品数反推人口**。
>
> **第 5 段的口径**：场地核查是**提醒，不是裁决**。报告中呈现为「硬伤 N 项 ｜ 风险 M 项 ｜ 待核实字段 K 项」，**禁止输出 `hard_vetoed` 式的"可否开业"结论**——证照由承租方办理，业务链条自己会卡。判断留给读报告的人，系统只负责说清「哪几个数还没有」。

**纪律**：报告里的每个数字必须能在 `probe.json` 找到出处；找不到就是编的。
