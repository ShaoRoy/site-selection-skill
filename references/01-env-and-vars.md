# 零、 环境预检与变量字典（执行前必读）

## 0.1 密钥自检（两把 Key，缺哪把报哪把）

| 数据源 | 角色 | 环境变量（优先） | 密钥文件（本机固定路径） |
| --- | --- | --- | --- |
| 高德 | **探路**：POI/竞品/交通 | `AMAP_API_KEY` | `C:\Users\Administrator\.dsh\secrets\amap.key` |
| 腾讯位置服务 | 周边 POI 交叉校验（不做人口测算） | `TENCENT_MAP_KEY` | `C:\Users\Administrator\.dsh\secrets\tencent.key` |

读取规则（两文件相同）：**跳过空行与 `#` 注释，取第一条有效行并去首尾空白**；仍是 `PUT_YOUR_AMAP_KEY_HERE` / `TENCENT_KEY_HERE` 或没有有效行 = 未配置。

未配置时只回这一句，不继续分析：

> ⚠️ 未检测到高德 API Key。请二选一：① 填进 `C:\Users\Administrator\.dsh\secrets\amap.key`；② 设环境变量 `AMAP_API_KEY`（`setx` 后重启宿主）。
> ⚠️ 未检测到腾讯位置服务 Key。请二选一：① 填进 `C:\Users\Administrator\.dsh\secrets\tencent.key`；② 设环境变量 `TENCENT_MAP_KEY`（`setx` 后重启宿主）。

**保密（强制）**：Key 只用于拼 URL / 工具入参；不得出现在回答、报告、日志、文件名或任何新建文件中；报告只写「（GIS 数据源：高德/腾讯，Key 已配置）」。

## 0.2.2 纠错口子（三层，缺一不可）

模型理解用户意图经常出错，所以**不要指望一次问对，要让纠正成本接近零**。每次测算必须同时给出下面三样：

1. **假设台账 `assumption_ledger`**——把本次所有「不是用户亲口给的数」摊在桌面上：
   - `财务参数`：未提供 → 落业态默认，动作标「必须补」；提供了但置信度低 → 「建议核实」
   - `租期系数 / 空间系数`：本次用了哪些内置缺省值，逐个列出实际取值
   - `参数覆盖`：哪些键被 params 文件覆盖、版本号是什么
   - `口径`：目标回本周期来自哪里
   **报告必须原样呈现这张表**，让用户一眼扫出「哪条是我没说过、被模型替他定的」。

2. **敏感度 `sensitivity` + `space_sensitivity`**——把关键参数各扰动 ±20%，看结论会不会翻。
   - `sensitivity`（财务侧）：日营业额、毛利率、人力、初始投入 → 看「租金是否高于锚点」翻不翻。
   - `space_sensitivity`（空间侧）：每座面积、厨房占比、常规翻台 → 看座位数与「应有日营收」怎么变、
     「面积与营收是否自洽（占比 ≥40%）」翻不翻。
   - 目的是回答「改哪一条值得」：会翻转的参数优先核，不翻转的可以先放着。
   - **「不变」本身也是结论**：如果三个空间系数各调 ±20% 都翻不动，说明问题不是系数不准，
     而是营收或面积差了一个数量级——此时禁止再用调参去"修"结论。
   - 只放**输入侧不确定的量**。**租金不要放进锚点敏感度**——它是结论的对象，不是锚点的输入。

3. **参数覆盖 `overrides`**——一处改、全链重算。分三层：
   - 业态级：`params/<业态>.json`（跨项目复用）
   - 单店级：`params/<store_id>.json`（同一业态不同点位差异大时用，优先于业态级）
   - 本次级：调用时直接传 `overrides`（一次性试验）
   三者优先级：本次 > 单店 > 业态 > 内置。

**最重要的一条纪律**：用户纠正某个数之后，**必须重跑并输出前后对比**，不能只在对话里"嗯我改一下"然后口头给新结论。没重跑 = 没改。

## 0.2.3 经验系数的参数覆盖（改系数不必改代码）

所有经验系数——目标回本、租售比两条线、厨房占比、每座面积、常规翻台、翻台上限、桌均人数、坪效基准、典型客单区间、租期/递增/翻新——都可经 `financial_calc` 的 **`overrides`** 入参覆盖。

- 参数文件放在与本文同目录的 `params/<业态>.json`，从 `_template.json` 复制；字段说明见 `params/README.md`。
- **优先级**：显式入参 > `params` 文件 > 内置默认，**逐字段生效**（没写的键才走默认）。
- 工具返回 `param_overrides_applied`（本次生效的键）与 `param_version_source`（版本号），**报告必须原样引用**，否则结论无法追溯。
- 三条纪律：① 改数必须升 `param_version`；② `param_source` 写清依据（老板口述 / 同行对标 / 实测）；③ **禁止为了凑结论反向调参**——参数是校准现实的，不是校准结论的。
- 找不到对应业态文件时，用内置默认照跑，但报告必须注明「未按业态校准，使用内置示例系数」。

## 0.2.4 内部比值校验：用参数互锁代替外部采样（本版核心）

**餐饮选址里外部数据不可靠**：点评评分与月售可刷、二手房挂牌价有结构性偏差、人口数据需企业付费。所以验证参数**不能靠再抓一份数据**，要靠内部比值互锁。

`financial_calc` 返回 `ratio_checks`，把已录入参数两两相除，与业态区间比对：

| 指标 | 算法 | 能抓出什么错 |
|---|---|---|
| 毛利率 | 取参数 | 是否虚高（没扣折扣/损耗） |
| **人力占营收** | 人力 ÷ 月营业额 | **人力估少了**（低于区间下限即确诊） |
| 租售比 | 租金 ÷ 月营业额 | 租金是否超警戒线 |
| **单方造价** | 初始投入 ÷ 建筑面积 | **投入漏项**（低于区间下限即确诊） |

**越界必须给反推值**，例如「人力占营收 10.9%，常规 22~30% → 按 22% 反推应为 15 万/月」。只说"偏低"没用，要告诉客户该改成多少。

业态区间全部可经 overrides 覆盖：`gross_margin_min/max`、`labor_ratio_min/max`、`investment_per_sqm_min/max`。**不许写死**——茶饮人力 15~25%、粤菜大店 22~30%、便利店 8~15%，差一倍。

### 数据来源纪律（硬性）

| 数据 | 怎么做 | 是否采用 |
|---|---|---|
| 住宅/写字楼/商场/学校/地铁 POI 密度 | `tools/demand-fetch.py`（高德，免费，全自动） | ✅ 采用 |
| 职住比 / 配套成熟度 / 咖啡与银行密度 | 同上，自动计算 | ✅ 采用 |
| 街道常住人口 | 政府公报多为图片/PDF，无免费接口 | ⛔ 放弃，用职住比替代 |
| **点评评分 / 月售 / 评论** | 评分与评论可刷，月售为外卖口径 | **⛔ 一律不采、不抓、不作为验证依据** |
| 二手房挂牌价 | 人工采样 10~15 个小区，可选 | ⚠️ 仅作辅助，需标注结构偏差 |

**一句话**：**需求侧用 POI 代理（自动、免费、抗刷），参数侧用内部比值互锁（不依赖外部）。不要用可刷的数据去验证不可刷的模型。**

## 0.2.5 行业基准对标（现实性校验，不替代单店参数）

`benchmark_check` 把本项目算出的数，放进 **19 城 × 48 业态**的行业基准库里逐项比对。

- 数据来源：`src/benchmark-data.ts`（由 `tools/import-benchmarks.py` 从 Excel 底稿生成，**勿手改**）
- 比对项：营业面积 / 初始投资 / 月租金 / 客单价 / 月营业额 / 会计口径回本 / 净利率
- 判定：偏离超 ±30% 报警（底稿自述单店实际受点位、转让金、装修档次影响 ±30%）

**用法纪律**：
1. 它是**现实性校验**，不是参数来源。发现偏离要先问「是我们估错了，还是这个项目本来就特殊」
2. 偏离方向不同含义不同：面积偏大 = 单位产出被摊薄；投资偏低 = 大概率漏项；回本偏短 = 口径或营收偏乐观
3. **不许拿基准值反向覆盖客户实测值**——基准是行业平均，客户自己的数是事实

典型输出（珠江新城 1500㎡ 粤菜）：

```
对标「粤式茶楼早茶」（正餐酒楼），样本 19 城，回本中位 51.9 月
营业面积 1500㎡ vs 400㎡  +275%   ← 面积选大了
初始投资 380 万 vs 150 万  +153%
会计回本 57.4 月 vs 49.7 月 +15.5%  ✅ 正常
```

**回本这一项落回基准，说明 fin-v3 的口径（含税费与摊销）是对的；面积与投资那几项偏离，才是真正要跟客户谈的问题。**

## 0.2.6 采集可信度与配额（防静默失败）

高德/腾讯在 **Key 失效、日配额耗尽、坐标错误**时，可能返回 `status=1` 但 `count=0`。静默出 0 会让报告得出「这里没有竞品」的荒谬结论——这是本系统最隐蔽的失败模式。

两条采集链路都必须输出 `data_quality`：

| 来源 | 字段 |
|---|---|
| `demand-fetch.py` | `api_calls / ok / failed / retried / zero_categories / all_zero / verdict` |
| `guangzhou-probe.mjs` | `verdict / amap{count,fetched,coverage} / tencent{…} / warnings` |

判定等级：

| verdict | 含义 | 处理 |
|---|---|---|
| `ok` | 各源均有返回 | 正常出结论 |
| `partial` | 部分源为空，或覆盖率 < 50% | 结论打折，注明缺口 |
| `suspicious` | **两源皆空** | 几乎一定是接口没给数据，**停止分析**，先查配额/权限/坐标 |
| `degraded` | 有请求失败 | 指标不完整，不可用 |

**报告第 1 段必须显示「采集可信度」一行；verdict ≠ ok 时，第 0 段结论下方直接打警告**——不允许在可疑数据上给结论。

配额常识：高德 Web 服务 POI 检索个人额度常见 **5000 次/日**。脚本已带 0.6s 节流 + 指数退避，撞 QPS 会自动重试；但**日配额耗尽不报错、只返回 0**，必须靠上面的 `data_quality` 识别。

## 0.2.7 现场反馈：自然语言怎么给才不丢信息

现场不用填表，**口述就行**，但每一条要说清四件事：

| 要素 | 说明 | 例子 |
|---|---|---|
| ① 目标 | 要能对上号（竞品名/站名+出口/小区名+哪个门） | 「猎德站 A 出口」而不是「猎德站」 |
| ② 通不通 | 直达 / 要绕 / 完全过不去 | 「过不去」「得绕一大圈」 |
| ③ 多远多久 | 尽量给数；给不了就说"没量" | 「走过去大概十分钟」 |
| ④ 什么挡着 | 护栏 / 高架 / 小区封闭 / 红灯多 / 没人行道 | 「中间是快速路，要绕到天桥」 |

**好例子**（Agent 可直接落成数据）：

> 从点位往南，猎德站 A 出口，直线一百来米，走过去要绕到猎德大道的天桥，实测三百多米、四分钟，中间是快速路。
> 珠江公园北门那边直通，六百米八分钟，没障碍。

**坏例子**（信息不够，Agent 只能追问或留空）：

> 对面都过不去。
> —— 哪个方向？哪个目标？绕多远？挡的是什么？全缺。

**Agent 的处理纪律**：

1. 口述里的数字照录，**没给数字就留空并在报告标注「口述未量化」**，不许按经验补一个
2. 目标名解析不到具体点位（如只说"地铁站"）→ 追问出口，或按站点中心点取并标「未确认出口」
3. 口述后有坐标的，跑 `tools/walk-matrix.py` 补算精确步行距离；两者不一致时**以实测/口述为准**，脚本值只作参考
4. 落盘成 `survey/barriers/<store_id>.csv`，`run-site.mjs` 会自动读进报告 2.5 段

**报告里会变成什么**：

```
### 2.5 动线阻断（现场实测）
| 猎德站A出口 | metro | 115m | 312m / 4.2分 | 2.71× | fence |
修正结论：3 个目标实际不可直达——猎德站A出口（2.71倍）、新天地潮菜（2.32倍）…
> 该方向应视为「不可步行到达」，份额与截流以本表为准，不以路网估算为准。
```

**这就是「自然语言进、评估报告出」的完整链路。**

## 0.2.8 网格扫描与覆盖管理（第 1 筛）

**不给具体商圈时**，用网格扫描找候选；**跑过的留在 registry，不重复花钱**。

### 四个入口，其余全藏在里面

```
1. 评估一个点   node tools\run-site.mjs --address=... --survey=...
2. 扫一片       python tools\grid-scan.py --city 广州 --district 天河
3. 记现场       python tools\walk-matrix.py ...
4. 看进度       node tools\index-dashboard.mjs   → out/index.md
```

### 硬规矩

1. **`grid-scan` 默认 dry-run**：先看调用预估。> 500 次要 `--yes`，> 1500 次直接拒绝。
2. **改权重用 `--rescore`**（0 次调用），不要重跑采集。
3. **分数是本批相对值**：不要跨批次比分数，A/B/C 按排名分档。
4. **网格只回答「去哪找」**：租金、铺位、层高、排烟属第 2、3 筛，不进本段。
5. **每跑一次自动留痕**：`status.json` + `registry.json` + `index.md`，不允许手工维护。

### 编号

`G{floor((lat+90)/0.005)}_{floor((lng+180)/0.005)}`，全球唯一、不随城市边界变化。
公式真源是 `tools/grid-registry.py`，`run-site.mjs` 的复刻由 `test-grid.mjs` 断言一致。

### 状态机

`未扫描 → 已扫描 → 已评估 → 已现场 → 候选池 / 已否决 / 已签约`，
由工具自动推进，`history` 只追加不覆盖。

## 0.2.9 截流两轴：点位截流力 × 竞争截流压力

**这是两个维度，不能互相替代，报告里必须分开写。**

| 轴 | 问的问题 | 数据来源 | 输出 |
|---|---|---|---|
| **第一轴·点位截流力** | 这个铺位能自然截住多少路过客流？ | **现场判定**（动线位置、可视、楼层、前置门店数） | L1~L5 + 客流乘数 |
| **第二轴·竞争截流压力** | 对手会抢走多少？ | POI 推算（最近竞品距离 + Top1/Top3 份额） | none / light / heavy |

### 第一轴：点位截流力（行业通用 5 级）

| 级 | 名称 | 典型场景 | 客流乘数 |
|---|---|---|---|
| L1 | 顶级截流（千分点） | 地铁直出口第一铺、商场主入口第一卡位、步行街转角铺、车库上来首铺 | ×1.30（1.25~1.40） |
| L2 | 强截流（A 类点） | 商场主通道中段、临街无隔离栏一楼铺、美食街主街中段 | ×1.10 |
| L3 | 中等截流（B 类·行业基准） | 商场餐饮区内侧铺、社区街铺非转角、主干道辅路铺、二楼临街铺 | ×1.00 |
| L4 | 弱截流（C 类点） | 商场高区末端、内街深处、隔护栏临街铺、同层同类店排在前面的 | ×0.65 |
| L5 | 极低截流（D 类·慎选） | 负一层死角、独立独栋远离动线、园区深处、商圈背街 | ×0.15 |

**调用方式**：`financial_calc` 传 `catchment_level: "L3"`；或调研表里写 `catchment_level`，`run-site` 自动带上。

**乘数作用在「行业常规日营业额」上**，把它调成这个点位实际能拿到的客流。

> ⚠️ **重复调整陷阱**：如果客户已经给出**实测日营业额**，就不要再传 `catchment_level`——
> 实测值里已经含了位置因素，再乘一遍等于双重打折。

### 第二轴：竞争截流压力（代码里叫 interception）

判 `none / light / heavy` 三级，阈值固定且随结果返回：

```
heavy：最近竞品 < 300m（贴脸）｜Top1 ≥ 30%｜Top3 ≥ 60%
light：最近竞品 < 800m        ｜Top1 ≥ 15%｜Top3 ≥ 40%
```

### 常见误用

| ❌ 错 | ✅ 对 |
|---|---|
| 用 L4 替代"重度截流" | L4 说场地差，heavy 说对手强，两回事 |
| 看到 heavy 就说不能开 | heavy 只说明竞争激烈，L1 位置照样能打 |
| 已给实测营业额又传 L 级 | 二者选一 |
