## 0.2.2 纠错口子（三层，缺一不可）

模型理解用户意图经常出错，所以**不要指望一次问对，要让纠正成本接近零**。每次测算必须同时给出下面三样：

1. **假设台账 `assumption_ledger`**——把本次所有「不是用户亲口给的数」摊在桌面上：
   - `财务参数`：未提供 → 落业态默认，动作标「必须补」；提供了但置信度低 → 「建议核实」
   - `租期系数 / 空间系数`：本次用了哪些内置缺省值，逐个列出实际取值
   - `参数覆盖`：哪些键被 params 文件覆盖、版本号是什么
   - `口径`：目标回本周期来自哪里
   **报告必须原样呈现这张表**，让用户一眼扫出「哪条是我没说过、被模型替他定的」。

2. **敏感度 `sensitivity` + `space_sensitivity`**——把关键参数各扰动 ±20%，看结论会不会翻。
   - `sensitivity`（财务侧）：日营业额、毛利率、人力、初始投入 → 看「租金是否高于锚点」翻不翻。
   - `space_sensitivity`（空间侧）：每座面积、厨房占比、常规翻台 → 看座位数与「应有日营收」怎么变、
     「面积与营收是否自洽（占比 ≥40%）」翻不翻。
   - 目的是回答「改哪一条值得」：会翻转的参数优先核，不翻转的可以先放着。
   - **「不变」本身也是结论**：如果三个空间系数各调 ±20% 都翻不动，说明问题不是系数不准，
     而是营收或面积差了一个数量级——此时禁止再用调参去"修"结论。
   - 只放**输入侧不确定的量**。**租金不要放进锚点敏感度**——它是结论的对象，不是锚点的输入。

3. **参数覆盖 `overrides`**——一处改、全链重算。分三层：
   - 业态级：`params/<业态>.json`（跨项目复用）
   - 单店级：`params/<store_id>.json`（同一业态不同点位差异大时用，优先于业态级）
   - 本次级：调用时直接传 `overrides`（一次性试验）
   三者优先级：本次 > 单店 > 业态 > 内置。

**最重要的一条纪律**：用户纠正某个数之后，**必须重跑并输出前后对比**，不能只在对话里"嗯我改一下"然后口头给新结论。没重跑 = 没改。

## 0.2.3 经验系数的参数覆盖（改系数不必改代码）

所有经验系数——目标回本、租售比两条线、厨房占比、每座面积、常规翻台、翻台上限、桌均人数、坪效基准、典型客单区间、租期/递增/翻新——都可经 `financial_calc` 的 **`overrides`** 入参覆盖。

- 参数文件放在与本文同目录的 `params/<业态>.json`，从 `_template.json` 复制；字段说明见 `params/README.md`。
- **优先级**：显式入参 > `params` 文件 > 内置默认，**逐字段生效**（没写的键才走默认）。
- 工具返回 `param_overrides_applied`（本次生效的键）与 `param_version_source`（版本号），**报告必须原样引用**，否则结论无法追溯。
- 三条纪律：① 改数必须升 `param_version`；② `param_source` 写清依据（老板口述 / 同行对标 / 实测）；③ **禁止为了凑结论反向调参**——参数是校准现实的，不是校准结论的。
- 找不到对应业态文件时，用内置默认照跑，但报告必须注明「未按业态校准，使用内置示例系数」。

## 0.2.4 内部比值校验：用参数互锁代替外部采样（本版核心）

**餐饮选址里外部数据不可靠**：点评评分与月售可刷、二手房挂牌价有结构性偏差、人口数据需企业付费。所以验证参数**不能靠再抓一份数据**，要靠内部比值互锁。

`financial_calc` 返回 `ratio_checks`，把已录入参数两两相除，与业态区间比对：

| 指标 | 算法 | 能抓出什么错 |
|---|---|---|
| 毛利率 | 取参数 | 是否虚高（没扣折扣/损耗） |
| **人力占营收** | 人力 ÷ 月营业额 | **人力估少了**（低于区间下限即确诊） |
| 租售比 | 租金 ÷ 月营业额 | 租金是否超警戒线 |
| **单方造价** | 初始投入 ÷ 建筑面积 | **投入漏项**（低于区间下限即确诊） |

**越界必须给反推值**，例如「人力占营收 10.9%，常规 22~30% → 按 22% 反推应为 15 万/月」。只说"偏低"没用，要告诉客户该改成多少。

业态区间全部可经 overrides 覆盖：`gross_margin_min/max`、`labor_ratio_min/max`、`investment_per_sqm_min/max`。**不许写死**——茶饮人力 15~25%、粤菜大店 22~30%、便利店 8~15%，差一倍。

### 数据来源纪律（硬性）

| 数据 | 怎么做 | 是否采用 |
|---|---|---|
| 住宅/写字楼/商场/学校/地铁 POI 密度 | `tools/demand-fetch.py`（高德，免费，全自动） | ✅ 采用 |
| 职住比 / 配套成熟度 / 咖啡与银行密度 | 同上，自动计算 | ✅ 采用 |
| 街道常住人口 | 政府公报多为图片/PDF，无免费接口 | ⛔ 放弃，用职住比替代 |
| **点评评分 / 月售 / 评论** | 评分与评论可刷，月售为外卖口径 | **⛔ 一律不采、不抓、不作为验证依据** |
| 二手房挂牌价 | 人工采样 10~15 个小区，可选 | ⚠️ 仅作辅助，需标注结构偏差 |

**一句话**：**需求侧用 POI 代理（自动、免费、抗刷），参数侧用内部比值互锁（不依赖外部）。不要用可刷的数据去验证不可刷的模型。**

## 0.2.5 行业基准对标（现实性校验，不替代单店参数）

`benchmark_check` 把本项目算出的数，放进 **19 城 × 48 业态**的行业基准库里逐项比对。

- 数据来源：`src/benchmark-data.ts`（由 `tools/import-benchmarks.py` 从 Excel 底稿生成，**勿手改**）
- 比对项：营业面积 / 初始投资 / 月租金 / 客单价 / 月营业额 / 会计口径回本 / 净利率
- 判定：偏离超 ±30% 报警（底稿自述单店实际受点位、转让金、装修档次影响 ±30%）

**用法纪律**：
1. 它是**现实性校验**，不是参数来源。发现偏离要先问「是我们估错了，还是这个项目本来就特殊」
2. 偏离方向不同含义不同：面积偏大 = 单位产出被摊薄；投资偏低 = 大概率漏项；回本偏短 = 口径或营收偏乐观
3. **不许拿基准值反向覆盖客户实测值**——基准是行业平均，客户自己的数是事实

典型输出（珠江新城 1500㎡ 粤菜）：

```
对标「粤式茶楼早茶」（正餐酒楼），样本 19 城，回本中位 51.9 月
营业面积 1500㎡ vs 400㎡  +275%   ← 面积选大了
初始投资 380 万 vs 150 万  +153%
会计回本 57.4 月 vs 49.7 月 +15.5%  ✅ 正常
```

**回本这一项落回基准，说明 fin-v3 的口径（含税费与摊销）是对的；面积与投资那几项偏离，才是真正要跟客户谈的问题。**

## 0.2.6 采集可信度与配额（防静默失败）

高德/腾讯在 **Key 失效、日配额耗尽、坐标错误**时，可能返回 `status=1` 但 `count=0`。静默出 0 会让报告得出「这里没有竞品」的荒谬结论——这是本系统最隐蔽的失败模式。

两条采集链路都必须输出 `data_quality`：

| 来源 | 字段 |
|---|---|
| `demand-fetch.py` | `api_calls / ok / failed / retried / zero_categories / all_zero / verdict` |
| `guangzhou-probe.mjs` | `verdict / amap{count,fetched,coverage} / tencent{…} / warnings` |

判定等级：

| verdict | 含义 | 处理 |
|---|---|---|
| `ok` | 各源均有返回 | 正常出结论 |
| `partial` | 部分源为空，或覆盖率 < 50% | 结论打折，注明缺口 |
| `suspicious` | **两源皆空** | 几乎一定是接口没给数据，**停止分析**，先查配额/权限/坐标 |
| `degraded` | 有请求失败 | 指标不完整，不可用 |

**报告第 1 段必须显示「采集可信度」一行；verdict ≠ ok 时，第 0 段结论下方直接打警告**——不允许在可疑数据上给结论。

配额常识：高德 Web 服务 POI 检索个人额度常见 **5000 次/日**。脚本已带 0.6s 节流 + 指数退避，撞 QPS 会自动重试；但**日配额耗尽不报错、只返回 0**，必须靠上面的 `data_quality` 识别。

## 0.2.7 现场反馈：自然语言怎么给才不丢信息

现场不用填表，**口述就行**，但每一条要说清四件事：

| 要素 | 说明 | 例子 |
|---|---|---|
| ① 目标 | 要能对上号（竞品名/站名+出口/小区名+哪个门） | 「猎德站 A 出口」而不是「猎德站」 |
| ② 通不通 | 直达 / 要绕 / 完全过不去 | 「过不去」「得绕一大圈」 |
| ③ 多远多久 | 尽量给数；给不了就说"没量" | 「走过去大概十分钟」 |
| ④ 什么挡着 | 护栏 / 高架 / 小区封闭 / 红灯多 / 没人行道 | 「中间是快速路，要绕到天桥」 |

**好例子**（Agent 可直接落成数据）：

> 从点位往南，猎德站 A 出口，直线一百来米，走过去要绕到猎德大道的天桥，实测三百多米、四分钟，中间是快速路。
> 珠江公园北门那边直通，六百米八分钟，没障碍。

**坏例子**（信息不够，Agent 只能追问或留空）：

> 对面都过不去。
> —— 哪个方向？哪个目标？绕多远？挡的是什么？全缺。

**Agent 的处理纪律**：

1. 口述里的数字照录，**没给数字就留空并在报告标注「口述未量化」**，不许按经验补一个
2. 目标名解析不到具体点位（如只说"地铁站"）→ 追问出口，或按站点中心点取并标「未确认出口」
3. 口述后有坐标的，跑 `tools/walk-matrix.py` 补算精确步行距离；两者不一致时**以实测/口述为准**，脚本值只作参考
4. 落盘成 `survey/barriers/<store_id>.csv`，`run-site.mjs` 会自动读进报告 2.5 段

**报告里会变成什么**：

```
### 2.5 动线阻断（现场实测）
| 猎德站A出口 | metro | 115m | 312m / 4.2分 | 2.71× | fence |
修正结论：3 个目标实际不可直达——猎德站A出口（2.71倍）、新天地潮菜（2.32倍）…
> 该方向应视为「不可步行到达」，份额与截流以本表为准，不以路网估算为准。
```

**这就是「自然语言进、评估报告出」的完整链路。**

## 0.2.9 截流两轴：点位截流力 × 竞争截流压力

**这是两个维度，不能互相替代，报告里必须分开写。**

| 轴 | 问的问题 | 数据来源 | 输出 |
|---|---|---|---|
| **第一轴·点位截流力** | 这个铺位能自然截住多少路过客流？ | **现场判定**（动线位置、可视、楼层、前置门店数） | L1~L5 + 客流乘数 |
| **第二轴·竞争截流压力** | 对手会抢走多少？ | POI 推算（最近竞品距离 + Top1/Top3 份额） | none / light / heavy |

### 第一轴：点位截流力（行业通用 5 级）

| 级 | 名称 | 典型场景 | 客流乘数 |
|---|---|---|---|
| L1 | 顶级截流（千分点） | 地铁直出口第一铺、商场主入口第一卡位、步行街转角铺、车库上来首铺 | ×1.30（1.25~1.40） |
| L2 | 强截流（A 类点） | 商场主通道中段、临街无隔离栏一楼铺、美食街主街中段 | ×1.10 |
| L3 | 中等截流（B 类·行业基准） | 商场餐饮区内侧铺、社区街铺非转角、主干道辅路铺、二楼临街铺 | ×1.00 |
| L4 | 弱截流（C 类点） | 商场高区末端、内街深处、隔护栏临街铺、同层同类店排在前面的 | ×0.65 |
| L5 | 极低截流（D 类·慎选） | 负一层死角、独立独栋远离动线、园区深处、商圈背街 | ×0.15 |

**调用方式**：`financial_calc` 传 `catchment_level: "L3"`；或调研表里写 `catchment_level`，`run-site` 自动带上。

**乘数作用在「行业常规日营业额」上**，把它调成这个点位实际能拿到的客流。

> ⚠️ **重复调整陷阱**：如果客户已经给出**实测日营业额**，就不要再传 `catchment_level`——
> 实测值里已经含了位置因素，再乘一遍等于双重打折。

### 第二轴：竞争截流压力（代码里叫 interception）

判 `none / light / heavy` 三级，阈值固定且随结果返回：

```
heavy：最近竞品 < 300m（贴脸）｜Top1 ≥ 30%｜Top3 ≥ 60%
light：最近竞品 < 800m        ｜Top1 ≥ 15%｜Top3 ≥ 40%
```

### 常见误用

| ❌ 错 | ✅ 对 |
|---|---|
| 用 L4 替代"重度截流" | L4 说场地差，heavy 说对手强，两回事 |
| 看到 heavy 就说不能开 | heavy 只说明竞争激烈，L1 位置照样能打 |
| 已给实测营业额又传 L 级 | 二者选一 |

## 0.2.10 三条已定口径（不要重开讨论）

1. **人口数据：不再寻找公开渠道。** 街道级真实人口没有可用的免费来源（政府公报多为图片/PDF，第三方为付费 B 端产品）。**用 POI 代理替代（住宅密度 + 职住比 + 配套 + 消费力品牌密度）**，不要再提"找人口数据"或"抓人口接口"。

2. **场地条件：只做提醒，不做否决；且只管场地，不管办证。** 详见 `docs/COMPLIANCE-CHECKLIST.md`。
   - **营业执照、食品经营许可证由承租方自行办理，与出租方无关，属签约后的行政跟进——不进选址报告，也不进现场核查清单。**
   - 报告只核**场地是否具备办证与经营的前置条件**：场地用途、面积与布局、排烟、上下水与排污、消防、燃气、外立面、居民距离。
   - 输出格式必须是「已核实 N 项 / 待核实 M 项 / 不适用 K 项」+ 缺口清单；
   - **不得**输出 `hard_vetoed` 式的裁决措辞（"不可开""硬性否决"）；
   - 理由：资料不齐的铺子本来就签不成、开不了业，业务链条自己会过滤。系统只负责把缺口列清楚。

3. **POI 楼层/体量信息：仅大型商超可得。** 高德能查大型商超的分层楼层与体量，**小体量门店没有楼层数据**。
   - 因此"地址/楼层维度去重"只在大商场多楼层场景下有实际意义；
   - **不要把它做成通用能力**，也不要在报告里对普通街铺输出楼层相关结论。

# 零点四、 计算口径全书（用这个 skill 的人必须先读这节）

> 目的：**任何人拿到这套工具，都能对着公式手算出同样的数**。
> 报告末尾的「附录：计算口径」会逐条打印「公式 + 本次代入值 + 结果」，与本节一致。

## 1. 情景因子（三档测算的缩放系数）

| 情景 | 营收因子 | 成本因子 |
|---|---|---|
| 基准 base | 1.00 | 1.00 |
| 保守 pessimistic | 0.85 | 1.05 |
| 乐观 optimistic | 1.15 | 0.97 |

## 2. 财务基础公式

每条都写成「一句话 + 中文算式 + 一个例子」，照着算就能复现。

**月营业额** = 日营业额 × 30
　例：22,000 × 30 = **660,000 元**

**月毛利** = 月营业额 × 毛利率
　例：660,000 × 0.62 = **409,200 元**

**月固定成本** = 月租金 + 人力成本 + 其他固定支出（物业费、水电等）
　例：150,000 + 72,000 + 28,000 = **250,000 元**

**月税费** = 月营业额 × 税费率（增值税及附加，默认 4.5%，可覆盖）
　例：660,000 × 4.5% = **29,700 元**

**月摊销** = 初始投入 ÷ 摊销月数（装修与设备按年限摊，默认 60 个月）
　例：3,800,000 ÷ 60 = **63,333 元**
　注意：摊销**不是现金支出**，只用于会计口径

**月现金净流** = 月毛利 − 月税费 − 月固定成本
　例：409,200 − 29,700 − 250,000 = **129,500 元**

**月净利（会计口径）** = 月现金净流 − 月摊销
　例：129,500 − 63,333 = **66,167 元**
　含义：这是财报上的净利，和行业净利率对标用这个

**保本日营业额** = 月固定成本 ÷ (毛利率 − 税费率) ÷ 30
　例：250,000 ÷ (0.62 − 0.045) ÷ 30 = **14,493 元/天**
　含义：一天做不到这个数，现金就是负的

**回本·现金口径（月）** = 初始投入 ÷ 月现金净流
　例：3,800,000 ÷ 129,500 = **29.3 个月**
　含义：**多久把投出去的钱收回来**，这是老板问的那个数

**回本·会计口径（月）** = 初始投入 ÷ 月净利（含摊销）
　例：3,800,000 ÷ 66,167 = **57.4 个月**
　含义：把折旧也算作回收对象，**和行业基准表可比**

**年化 ROI** = 月净利（会计）× 12 ÷ 初始投入
　例：66,167 × 12 ÷ 3,800,000 = **20.9%**

> **为什么给两个回本数**：摊销不是现金流出，拿它算"多久回本"会虚长；
> 但算净利率又必须扣它，否则和行业口径对不上。**两个都给，不许混用**。
> 谈租金用现金口径，对标行业用会计口径。

> **三档怎么来的**：保守情景把营业额 ×0.85、固定成本 ×1.05；乐观情景 ×1.15、×0.97。
> 上面每个公式在三档里各算一遍，所以每档都有一套「净利 / 保本 / 回本」。

## 3. 极限租金（把「净利」倒过来解「租金」）

**极限租金·保本** = 月毛利 − 人力成本 − 其他固定支出
　例：409,200 − 72,000 − 28,000 = **309,200 元/月**
　含义：租金超过这个数，这门生意就是亏的

**极限租金·目标回本** = 月毛利 − 初始投入 ÷ 目标月数 − 人力 − 其他固定
　例（想 36 个月回本）：409,200 − 3,800,000÷36 − 72,000 − 28,000 = **203,644 元/月**
　含义：想在这个期限内回本，租金不能超过这个数

**建议锚点** = 三档里最低的那个「目标回本租金上限」
　例：基准 203,644 ／ 保守 130,728 ／ 乐观 276,314 → 取 **130,728**
　含义：锚点不是"砍到这个价就签"，而是"高于这个价，压力测试下回本不成立"

> 保守/乐观档里，毛利要除以成本因子、固定支出要按因子换算，附录会直接给出算好的代入值。

两个值**都可能为负**：负值不是算错，是结论——即便零租金也达不到该口径，问题在营收或投入结构。报告须原样呈现，**不得归零**。

**建议锚点** = `min(各档极限租金·目标回本)`，跨档取最保守。锚点不是"砍到这个价就签"，是"高于这个价，压力测试下回本不成立"。

## 4. 租期现金流（解决"静态回本漂亮但租期内白干"）

**某一年要交的月租金** = 首年租金 × (1 + 年递增) 的「年数−1」次方
　例：第 3 年 = 150,000 × 1.03² = **159,135 元/月**

**该年的月净利** = 月毛利 − (该年租金 + 人力成本 + 其他固定支出)

**翻新**：每 5 年一次，在年末一次性扣掉（缺省按初始投入的 25% 估）
　例：第 5 年扣 3,800,000 × 25% = **950,000 元**

**租期回本月份**：把每月净利一路累加（起点是「−初始投入」），
　第一次变成正数的那个月；租期内一直没转正，就写「租期内未回本」

**期末累计现金** = 各年净利之和 − 初始投入 − 各次翻新之和
　负数 = 这份合同期内白干

判定：`fail` 期末为负；`tight` 回本月份 > 60% 租期；`healthy` 其余。

**两个独立检查**：
- 租期是否 ≥ 该面积下限（≥1000㎡ 建议 7 年，300~1000㎡ 5 年，小店 2~3 年）
- 租期是否容得下「回本 + 等长赚钱期」= `目标回本 × 2 ÷ 12` 年

## 5. 空间容量（把面积和营收对账）

**厨房面积** = 建筑面积 × 厨房占比
　例：1,500 × 35% = **525 ㎡**

**营业面积** = 建筑面积 − 厨房面积
　例：1,500 − 525 = **975 ㎡**

**座位数** = 营业面积 ÷ 每座面积（向下取整）
　例：975 ÷ 2.8 = **348 个**
　（如果客户直接报了座位数，就用他报的，不再推算）

**日均客流** = 日营业额 ÷ 客单价
　例：22,000 ÷ 252 = **87 人/天**

**翻台率** = 日均客流 ÷ 座位数
　例：87 ÷ 348 = **0.25 次/天**
　含义：每个座位一天只坐了 0.25 次

**应有日营收** = 座位数 × 该业态常规翻台 × 客单价
　例：348 × 2.0 × 252 = **175,392 元/天**
　含义：这个面积按行业常规，一天本该做到多少

**营收占比** = 实际日营业额 ÷ 应有日营收
　例：22,000 ÷ 175,392 = **12.5%**
　低于 40% → 判「面积与营收不匹配」

**保本翻台率** = 保本日营业额 ÷ 客单价 ÷ 座位数
　例：13,441 ÷ 252 ÷ 348 = **0.15 次/天**
　含义：一天至少坐满 15% 的座位才不亏

**坪效** = 月营业额 ÷ 建筑面积
　例：660,000 ÷ 1,500 = **440 元/㎡/月**

**单方造价** = 初始投入 ÷ 建筑面积
　例：3,800,000 ÷ 1,500 = **2,533 元/㎡**

> **桌翻台** =（客流 ÷ 每桌人数）÷ 桌数。当"每桌人数"与"座位数÷桌数"一致时，
> 它和座翻台**算出来是同一个数**，不要当成两个不同指标来回比。

## 6. 内部比值校验（不依赖外部数据，抓"参数估错"）

| 指标 | 怎么算 | 越界说明什么 |
|---|---|---|
| 毛利率 | 直接取填写的毛利率 | 虚高＝没扣折扣、赠送、损耗 |
| 人力占营收 | 人力成本 ÷ 月营业额 | 偏低＝人力估少了（会反推出「按区间下限应该是多少万」） |
| 租售比 | 月租金 ÷ 月营业额 | 超警戒线＝租金结构不安全 |
| 单方造价 | 初始投入 ÷ 建筑面积 | 偏低＝投入漏项（会反推出「按区间下限应该是多少万」） |

区间按业态取值，全部可经 `overrides` 覆盖（`gross_margin_min/max`、`labor_ratio_min/max`、`investment_per_sqm_min/max`）。

## 7. 敏感度（回答"改哪个参数会翻结论"）

- 财务侧：把**日营业额 / 毛利率 / 人力成本 / 初始投入**各调 ±20%，看「谈判锚点」会不会跨过当前租金 → 变了就说明这个参数最该先核
- 空间侧：把**每座面积 / 厨房占比 / 常规翻台**各调 ±20%，看座位数与应有日营收怎么变、以及「营收占比是否越过 40%」
- 报告会直接写出「会翻转 / 不变」，不用自己判断

**「不变」本身是结论**：三个空间系数都翻不动，说明差距是数量级级别，不是调参能解决的。

## 8. 口径纪律

1. 报告末尾必须打出「计算口径」附录，缺一行都算不合格
2. 任何公式改动必须升 `FORMULA_VERSION`（当前 `fin-v2`）
3. 缺省参数必须进 `assumption_ledger`，不许静默兜底
4. 代理指标必须标「代理」，不得当成实测

## 0.6 数据治理（L3：真实项目 80% 时间在这里，必须先做）

> **优先用工具，别手工数**：调用 `poi_dedupe`（本地确定性计算，不联网），把两源 POI 数组传进去；

### 0.6.1 POI 去重（先去重，再报竞品数）

1. **同名同点合并**：名称完全一致且坐标距离 ≤ 50m → 同一门店，只留 1 条。
2. **同名连锁分离**：同名但距离 > 50m → 保留，报告写「罗森（3 处）」，并给最近一处距离。
3. **跨源合并**：高德与腾讯同一 POI（名称相似度 ≥ 80% 且距离 ≤ 100m）→ 合并，sources 记 [高德, 腾讯]。
4. 必须输出三个数：`原始条数` / `去重后条数` / `合并掉条数`。

### 0.6.2 分类清洗（口径由用户定义，脚本不含业态假设）

`poi_dedupe` **默认不做任何类目过滤**，必须由调用方显式传两个正则（与 `{competitor_keywords}` 同属必填项，缺了就问）：

| 参数 | 作用 | 不传的后果 |
| --- | --- | --- |
| `category_pattern` | 竞品类目白名单（正例） | 全类目保留，`effective` 虚高 |
| `exclude_pattern` | 名称排除（**只匹配店名**） | 快餐/外卖等混入竞品数 |
| `exclude_category_pattern` | 类目排除（只匹配平台类目） | 慎用——类目用词不可靠，会误杀同类 |

> ⚠️ **类目排除要慎用**（实测教训 2026-10）：高德把"潮双喜澄海狮头鹅""湛江白切鸡"这类正经粤菜馆标成 `餐饮服务;小吃店`，用 `小吃` 做排除会把它们整批误剔。
> 白名单则相反：**必须包含平台通用词 `餐饮`**，否则大量餐厅（类目只写"餐饮相关场所"）会被漏掉。

⚠️ **白名单匹配的是平台的「类目字段」（高德 `type` / 腾讯 `category`），不是店名。**
品牌词（茶颜悦色、海底捞、广州酒家）只能放 `{competitor_keywords}` 去检索；放进白名单会把整类误剔。

实测教训（2026-10 广州，真实数据）：
- `category_pattern='茶饮|奶茶'` → 把类目为 `餐饮服务;冷饮店` 的奈雪、蜜雪、一点点**全剔掉**（45 条剩 4 条）
- `category_pattern='酒楼|宴会'` → 把类目为 `美食:中餐厅:粤菜` 的广州酒家、陶陶居、利苑**全剔掉**（剔 16 条）

**按用户业态填写（示例，禁止当默认值）**：

| 业态 | category_pattern（**类目词**） | exclude_pattern |
| --- | --- | --- |
| 便利店 | `便利店` | `超市|百货|2元|折扣` |
| 茶饮 | `冷饮|甜品|咖啡|茶饮|饮品` | `便利店|超市` |
| 中型正餐（80–200㎡） | `中餐厅|餐厅|快餐厅` | `快餐|小吃|外卖` |
| 大型正餐（1000–2000㎡） | `中餐厅|海鲜|粤菜|宴会|火锅` | `快餐|小吃` |
| 火锅 | `火锅|中餐厅` | `快餐|小吃` |
| 粉面 | `中餐厅|面馆|小吃` | `酒楼|宴会` |

**不确定类目长什么样时**：先把 `category_pattern` 留空跑一次，从 `kept` / `dropped` 里读出平台真实类目串，再定正则——不要凭想象写。

用户没给业态 → **必须先问**，不得套用上表任何一行，也不得默认「便利店」。
剔除必须列清单（名称 + 原因），**禁止静默丢弃**。

### 0.6.3 地理编码失败处理

- 回退链：详细地址 → 街道/道路 → 区县 adcode → 城市。
- **失败率 = 失败数 ÷ 总请求数；> 20% 必须停止分析**，先让用户修地址或换关键词。
- 报告必写：成功数 / 失败数 / 失败率 / 实际使用的回退层级。

### 0.6.4 脏数据规则

命中任一条标「可疑」并单列，**不计入竞品数**：坐标距离 = 0 且成批出现（≥5 条同坐标）、坐标落在水域或行政区外、电话与地址全空、同名但跨区。

## 0.7 坐标系与精度声明（L1 / L4）

> **工具优先**：输入坐标先过 `crs_guard`（基准 = 高德 GCJ-02）。`input_crs='wgs84'` 会自动转换并返回每点偏移量；转换后坐标才可用于高德/腾讯接口。报告中的「距离 X 米」必须建立在 GCJ-02 之上，坐标系未声明不得给距离。

## 0.8 空间分析（L2：本地计算，零调用成本）

> 用 `geo_analyze` 做三件事，**阶段二第 3 步之后调用**：
> ① **等时圈估算**：`mode`（walk/bike/car）+ `minutes` → 直线半径 = 速度 ÷ 绕行系数 1.35；缺省步行 10 分钟（约 593 米）。
> ② **竞争份额**：网格 Voronoi（默认 100m 格），**只统计等时圈内**，输出每家竞品占的面积与百分比；第一名份额 > 50% 表示单店垄断，< 25% 表示高度碎片化。
> ③ **距离矩阵**：竞品两两距离（前 20 点）。
> ④ **势力归属与截流定级**（本版新增，`competition` 字段）：
>    · `center_in_cell_of`：本点位落在**谁**的 Voronoi 势力范围内（即圈内最近的那家竞品）。落进谁的地盘，就说明客流大概率先被谁截走。
>    · `interception.level`：`none` 无截流 / `light` 轻度分流 / `heavy` 重度截流，判定同时看**距离**与**份额**：
>      - 重度：最近竞品 < 300m，或 Top1 份额 ≥ 30%，或 Top3 合计 ≥ 60%（任一触发即重度）
>      - 轻度：最近竞品 < 800m，或 Top1 ≥ 15%，或 Top3 ≥ 40%
>      - 其余为无截流
>    · `interception.reasons[]`：逐条列出触发条件，**报告必须原样引用**，不得只写等级不写理由。
>    · `thresholds`：本次使用的阈值快照，随结果返回，保证结论可复核。
>    ⚠️ 份额是「离谁近」的代理，不含品牌力与评价分；截流定级同样只是**空间代理**，不等于真实客流被抢。报告须注明这一点。
> ⚠️ 等时圈是**估算值**，报告中必须标【估算】，**不得**写成"路网精确等时圈"；份额也必须注明"在 X 米估算圈内统计"。
> ④ **双圈（商圈口径）**：**步行 10 分钟 ≈ 一个商圈的极限；车行 5 分钟同理；车行 10 分钟会跨 2–3 个商圈，不可用。**
>    · 内圈 `walk 10`（≈590 米）→ **报份额（W1–W8）**，看日常客流对手；
>    · 外圈 `car 5`（≈1850 米）→ **只报竞品数量 + 距离带分布，禁止报份额**，看宴请辐射。
>    **原因**：车行 10 分钟动辄 40 km²，含江面、公园与非商圈区域，份额分母被稀释，会得出"某家占 16.5%、格局分散"这类误导结论。
>    禁止把两圈数字混在同一句里比较，也禁止只报一个大圈就说"竞争饱和"。
> ⑤ **商圈锁（必用）**：等时圈 ∩ 固定半径——大型餐饮 内 1.0km / 外 2.0km；中型餐饮 0.8km / 1.8km；茶饮便利店 0.5km / 1.0km。
>    理由：路网可达 ≠ 客人愿意来。车行 5 分钟能开 2 公里，10 分钟能开到 5 公里外——那已经是另一个商圈，算进来是噪声。
>    实现：`LOCK_RADIUS=米` 环境变量可全局覆盖；默认取各圈层 `max_m`。
> ⑥ **交通可达（必查，进报告 2.2 段）**：**最近地铁站距离（阈值 800m）+ 最近停车场距离（阈值 300m）**。
>    人话口径：地铁 **>800m = 步行不友好**，员工难招；停车场 **>300m = 宴请客劝退**——走 300 米还没到车位，客人就不来了。
>    数据缺失时写"交通数据未取到"，禁止估算。

1. **坐标系**：高德与腾讯返回 **GCJ-02**（火星坐标）。若用户给的是 GPS 原始点（WGS84），必须先声明并按偏移提示风险（城市内约 50–500m）；**坐标系未声明，不得输出任何「距离 X 米」结论**。
2. **精度声明段**（每份报告必写）：数据源、取数时刻、圈层半径、样本量、坐标系、已知误差来源（POI 收录延迟 / 分类粒度 / 跨源口径 / 人口为区域级非点位级）。
3. **荒谬结果自检**：出现任一情况先怀疑口径，不得直接下结论——双源数量差异 > 50%、最近竞品 < 50m（多半同楼同商场）、去重前后差 > 40%、人口档位与竞品密度方向相反。

> ⚠️ 以上三节的约束视同红线：**未去重不得报竞品数；未声明坐标系不得报距离；地理编码失败率 > 20% 必须先停**。

## 0.9 否决规则包（`veto_check` 的 `rules` 入参，可外置）

内置 R001–R005 **只是示例**（便利店/正餐通用），不是标准。按业态传 `rules` 覆盖后，返回的 `rule_source` 为 `custom`。

| 字段 | 说明 |
| --- | --- |
| `id` / `desc` | 规则号与描述，原样进报告 |
| `field_key` | 依赖的调研字段代号（与 `fields` 的键一致） |
| `severity` | `hard` 硬性否决 / `major` 重大风险 |
| `op` | `absent` 无/空 · `lt` `gt` `lte` `gte` 数值比较 · `eq` 相等 · `contains` 包含 |
| `value` | 阈值（数值或字符串均可）；`absent` 不需要 |
| `formats` | 适用业态；空或省略 = 全部 |

**茶饮规则包（示例）**

```json
[
  {"id":"T1","desc":"无上下水条件","field_key":"water_supply","severity":"hard","op":"absent"},
  {"id":"T2","desc":"层高不足（<3.2m，做不了立面）","field_key":"ceiling_m","severity":"hard","op":"lt","value":3.2},
  {"id":"T3","desc":"无法办理外摆许可","field_key":"outdoor_permit","severity":"major","op":"absent"}
]
```

**大型正餐规则包（示例）**

```json
[
  {"id":"L1","desc":"消防疏散宽度不足（<1.4m）","field_key":"fire_egress_m","severity":"hard","op":"lt","value":1.4},
  {"id":"L2","desc":"燃气容量不足（<10m³/h）","field_key":"gas_m3h","severity":"hard","op":"lt","value":10},
  {"id":"L3","desc":"停车位不足（<30）","field_key":"parking_slots","severity":"major","op":"lt","value":30},
  {"id":"L4","desc":"无排烟管道井","field_key":"exhaust","severity":"hard","op":"absent"}
]
```

调用时同时传 `rules_version`（如 `tea-2026.11`），报告必须原样引用；`rule_source = custom` 时首段写「规则来源：用户自定义（版本 X）」，**不得冒充内置规则**。
用户没给规则包 → 用内置示例，但报告必须注明「使用内置示例规则，未按业态校准」——这本身就是一个风险提示。

## 0.10 阶段二工具链（固定顺序，一步都不能跳）

| 步 | 调用 | 产出 | 跳步的后果 |
| --- | --- | --- | --- |
| 1 | `crs_guard`（`input_crs` 默认 gcj02） | 统一坐标 + 偏移量 | 混基准 → 距离全错 |
| 2 | `veto_check` | `hard_vetoed` / `hard_reasons` | 硬伤漏判 |
| 3 | 高德 `place/around` | 原始 POI（source=amap） | 无第一源 |
| 4 | 腾讯 `place/v1/search` | 第二源 POI（source=tencent） | 无双源交叉 |
| 5 | `poi_dedupe`（两源合并传入） | `effective` / `brand_groups` / `dropped` | 竞品数虚高 |
| 6 | `geo_analyze`（`mode`/`minutes`） | 等时圈【估算】+ 圈内份额 + 距离矩阵 | 无空间结构 |

**自检**：报告里缺哪一段，就说明对应那一行的工具没调——必须补调后重写，不得用文字"大概说一下"糊过去。

## 0.11 数据 → 人话（强制翻译层）

面向不懂数据的老板：**每个数字后面必须跟一句「这意味着…」**，只给数字或只给术语视为不合格。

### 份额（内圈/外圈 Top1）

| Top1 份额 | 人话 |
| --- | --- |
| ≥ 50% | 一家独大。正面打很难，除非品类完全错位。 |
| 25–50% | 有强势玩家但没垄断。能做，但别开在它门口，靠差异化分客。 |
| < 25% | **没有垄断者：谁都能进来，但也谁都吃不饱。**靠差异化切一小块，别指望做头部。 |

### 圈内竞品数（步行 10–12 分钟圈）

| 家数 | 人话 |
| --- | --- |
| 0–3 | 几乎空档。**先确认为什么没人**——可能没需求，不是机会。 |
| 4–10 | 正常竞争。顾客有得选，靠口味和品类赢。 |
| 11–30 | 很密集。翻台靠位置和复购，新店必须有一个记忆点。 |
| > 30 | 贴脸红海。除非租金极低或有独家资源，否则别进。 |

### 最近竞品距离

| 距离 | 人话 |
| --- | --- |
| < 100m | 门对门抢客。胜负看品牌力和招牌可见度。 |
| 100–300m | 同街竞争，谁先被看见谁赢。 |
| > 500m | 各自成片，是商圈级竞争，不是直接对撞。 |

### 品牌集中度

| 信号 | 人话 |
| --- | --- |
| 同一品牌 ≥ 3 处 | 这个品牌已经在这片区铺开了，正面撞车。 |
| Top1 品牌占有效竞品 ≥ 30% | 连锁化程度高，夫妻店很难活。 |

### 财务与数据质量

| 指标 | 人话 |
| --- | --- |
| 保守档回本 < 24 个月 | 这个租金撑得住。 |
| 24–36 个月 | 偏紧，要么压租金，要么提客单。 |
| > 36 个月或无法回本 | 靠生意本身回不了本，除非你有别的理由。 |
| 双源数量差 > 50% | 这是统计口径差，不是竞品真翻倍——先查口径再下结论。 |
| 采集覆盖率 < 95% | 数据不全，漏掉的竞品没算进来，结论偏乐观。 |

### 句式（强制：专业表述 + 直白解释，**两者都要**）

> **结论**：能开 / 谨慎 / 别开（一句话）
> **判断**：每条 = 专业表述（术语 + 数值）—— 破折号 —— 人话解释
> **数据**：表格（给会看的人）

同一份报告要同时服务两类读者：专业人士看术语与数值，老板看人话。**只给一边都算不合格**。

- ❌ 只有术语：`内圈 Top1 份额 6.8%，属高度碎片化市场`
- ❌ 只有人话：`谁都吃不饱`
- ✅ 两者都给：`内圈 Top1 份额 6.8%（高度碎片化，<25%）——没有垄断者：谁都能进来，但谁都吃不饱。靠差异化切一小块，别指望做头部。`

其余字段同样处理：

- `最近竞品 88 米（<100m，贴脸级）——门对门抢客，胜负看品牌力和招牌可见度。`
- `步行 12 分钟圈 97 家（>30，贴脸红海）——顾客根本不缺选择，翻台靠记忆点，不靠位置。`
- `保守档回本 31 个月（24–36，偏紧）——这个租金撑得辛苦，要么压租金，要么提客单。`
- `采集覆盖率 91.1%（<95%，数据不全）——漏掉的竞品没算进来，实际竞争比看到的更狠。`

## 0.12 两级品类模型（同类＝竞品，异类＝协同）

**执行前必须问用户细分品类，不得沿用下表示例。** 大类决定"聚集度"，细分决定"竞争度"。

| 大类 | 细分（用户填） | subtype_pattern |
| --- | --- | --- |
| 大型餐饮·茶楼 | 粤式早茶 | `茶楼|茶居|点心` |
| 大型餐饮·粤菜 | 顺德菜 / 潮州菜 | `粤菜|顺德|潮州|烧腊` |
| 大型餐饮·火锅 | 牛肉火锅 | `牛肉|牛杂|潮汕` |
| 大型餐饮·火锅 | 海鲜火锅 | `海鲜|鱼头|粥底` |
| 中型餐饮·粉面 | 桂林米粉 / 兰州拉面 | `米粉|米线` / `拉面|牛肉面` |

**口径规则（写死）**

- **同类型（命中 `subtype_pattern`）＝竞品**：报告里的"竞品数"只用 `same_type_count`。
- **异类（大类内、细分外）＝协同**：带来客流、不抢客，单独报 `other_type_count`，并说明"餐饮聚集度"。
- `effective` = 同类 + 异类之和，**禁止直接当竞品数用**。
- 用户没给细分 → 必须先问；确实不细分时，报告须注明"未区分细分品类，竞品数可能高估"。

**人话口径**

- 同类 30 家 + 异类 150 家 → 竞争极烈但**客流旺**，靠差异化切一块。
- 同类 8 家 + 异类 5 家 → 品类空档，但**先确认有没有人流量**，可能不是机会。

## 0.13 业态档案（必须由客户信息生成，不得套用预设）

每个客户的业态、规模、客群都不同。**所有参数来自业态档案，不来自本文档**；本文档里的数字只是示例。

**执行第一步：先产出/确认业态档案**（存 `profiles/<名字>.json`，用 `--profile=<名字>` 调用）

**动手前先选一种建档方式**（手写 JSON 最容易漏必填项）：

| 方式 | 命令 | 适用 |
|---|---|---|
| **从现成档案复制**（推荐） | `node tools/profile-build.mjs --scaffold=large-yuecai` | 已有相近业态，只改半径/圈层 |
| 命令行建档 | `node tools/profile-build.mjs --name="..." --archetype=large-dining --subtype="..."` | 有起点库可套 |
| 手写 JSON | 照本节字段表逐个填 | 结构特殊 |
| 校验 | `node tools/profile-build.mjs --check=<名字>` | 改完必跑 |

**必填项只有两条**：`name`、`rings`。其余缺失会降级为警告并在报告里标出来，不会中止流程——包括 `category_pattern`（见 0.6.2 的「先留空跑一次」做法）。

```json
{
  "name": "大型餐饮·粤菜（1000–2000㎡）",
  "category_pattern": "中餐厅|粤菜|海鲜|宴会|酒楼",
  "exclude_pattern": "快餐|小吃",
  "subtype_pattern": "粤菜|顺德|潮州|烧腊",
  "keywords": ["粤菜", "海鲜", "酒楼", "宴会"],
  "scan_radius": 3000,
  "rings": [
    { "label": "内圈·步行10分", "mode": "walk", "minutes": 10, "max_m": 1000 },
    { "label": "外圈·车行5分", "mode": "car", "minutes": 5, "max_m": 1500 }
  ],
  "transit": { "metro_threshold_m": 800, "parking_threshold_m": 300 }
}
```

| 字段 | 作用 |
| --- | --- |
| `category_pattern` | 大类白名单（决定"餐饮聚集度"） |
| `exclude_pattern` | 排除非同类（快餐/超市…） |
| `subtype_pattern` | 细分品类（决定"真正竞品"）——**必须问客户** |
| `keywords` | 检索词，多个可提高覆盖率（配合 `--sweep`） |
| `scan_radius` | POI 采集半径 |
| `rings` | 圈层（出行方式 / 时长 / 商圈锁半径） |
| `transit` | 地铁与停车阈值（按业态定） |

**三条纪律**

1. 客户没给的信息 → **先问**，禁止沿用示例。
2. 阈值按业态走：早餐/茶饮要更近（步行 3–8 分钟、停车 100m）；大型餐饮可放宽（车行 5 分钟、停车 300m）。
3. 报告必须写明「本次使用的业态档案：<name>」，否则结论无法复核。

## 0.14 建档流程（每个客户第一步，不得跳过）

**建档 → 给建议 → 再分析**，顺序不能反。

**① 问客户 6 件事 + 5 个硬件项**（一次最多问 3 个，缺一不可）

经营面：
1. 业态与主打品类（例：潮汕牛肉火锅 / 粤式早茶 / 柠檬茶）
2. 门店面积与座位数（决定圈层与停车阈值）
3. 客人主要怎么来（走路 / 开车 / 地铁 / 混合）
4. 城市与候选区域
5. 差异化是什么（价格带、场景、时段——决定除 subtype 外的对比维度）
6. 可承受月租金（反向校验商圈：高租金对应高客流圈）

工程硬件（决定「这个铺能不能做」，建档时一次问清，写进 `profile.hardware`）：
7. 目标面积㎡——**≥300㎡ 通常触发二次消防备案，≥1000㎡ 多需消防设计审查**
8. 是否需要排烟
9. 需要电力多少 kW（按有管道燃气估算）
10. 是否需要管道天然气——**没有燃气，厨房全电，电力需求额外 +100kW**
11. 是否需要排污 / 隔油池；层高要求；门宽 / 承重 / 外立面等其他硬性条件
12. **可接受的合同年限**（大面积业态 7~10 年，小店 2~3 年）
13. **该商圈/该房东的租金年递增惯例**（没有就用 3% 均值，但必须在报告里标为缺省）
14. **翻新周期与单次翻新预算**（4~5 年一次，缺省按初始投入 25% 估，同样要披露）

问完立即打印**现场核查清单**（`profile-build.mjs` 会自动生成），交开发带去现场逐条核实；核实结果填进调研表的 `fields`（`exhaust` / `power_kw` / `area_sqm` / `frontage_m` / `ceiling_m` / `gas_m3h` / `water_supply` / `fire_egress_m`）再喂 `veto_check`。

**② 建档**

```powershell
node .\tools\profile-build.mjs --ask
node .\tools\profile-build.mjs --name="早餐·肠粉" --archetype=breakfast --subtype="肠粉|布拉肠" --area=40
```

**③ 把建议讲给客户听**——建档器会打印每条参数的"为什么"，不能只甩数字：

- 为什么这个圈层（早餐 3/8 分钟 ≈ 900m；大型正餐 步行10 + 车行5）
- 为什么这个停车阈值（早餐 80m；大型正餐 300m）
- 细分品类为什么这么定（同类＝竞品，异类＝协同）

**④ 校验 + 分析**

```powershell
node .\tools\profile-build.mjs --check=<slug>
node .\tools\guangzhou-probe.mjs "<地址>" --profile=<slug>
```

**⑤ 报告首行必须写**：`本次使用业态档案：<name>（<slug>）`

**反例**：客户说"我做火锅"就直接套大型餐饮档案 → 错。火锅有牛肉/海鲜/自助之分，客群与商圈完全不同，必须先问清细分再建档。

## 0.15 唯一入口（架构约定）

| 0 | 结论 | 综合 | — |

# 一、 强制工作流 SOP（自动判定阶段）

## 【阶段一：商圈初选】
- **触发条件**：仅有城市/区域，无具体铺位坐标。
- **执行**：地理编码转坐标 → 高德扫 POI 密度与交通枢纽（`keywords=地铁站`）→ 若 MCP 可用，顺带取该区域 1000m 实时人口做粗筛。
- **拦截**：无坐标不做空间分析、不算财务。

## 【阶段二：现场复核】
- **触发条件**：有地址/经纬度，但无准确租金或全套财务参数。
- **执行（按序）**：
  1. `veto_check`（`store_id`/`format_code`/`fields`：`exhaust`、`power_kw`、`rent`、`frontage_m`、`area_sqm`）排硬伤；
  2. **高德探路 + 去重**：`{gis_radius}` + `{competitor_keywords}` 取原始 POI → 传给 `poi_dedupe` → 用 `effective` 作为**有效竞品数**、`brand_groups` 作为品牌集中度；报告中竞品数一律用 `effective`，**不得用原始条数**；
  4. **双源交叉**：竞品数差异 > 30% 必须说明口径（半径上限 1000m、分类粒度、关键词），不得只取其一；
  5. **预警判定**：竞品 ≥ `{warning_threshold}` → 【截流预警】；人口「低」→ 【需求不足预警】；T ≥ 3 → 【业态时段错配风险】；画像不匹配 → 【客群结构错配】。
- **拦截**：无财务参数不输出回本周期。

## 【阶段三：最终锁盘】
- **触发条件**：有准确租金、物业费、转让费、客单价、毛利率、装修投入。
- **执行**：`financial_calc` 三档（`monthly_rent`=租金；`monthly_other_fixed`=物业费+其他固定；`initial_investment`=装修+转让费+设备；`gross_margin`=毛利率；`daily_revenue`=客单价×日均客流，换算需写明）→ 用 `breakeven_revenue_daily` 反推极限租金 → 把双源结论并入谈判筹码。
- **极限租金（本版新增，`rent_ceiling`）**：显式传入 `target_payback_months`（默认 24），返回两个上限——
  · `rent_ceiling_breakeven`：净利 = 0 时的租金上限（再高一分钱就是亏）；
  · `rent_ceiling_at_target`：回本恰好等于目标月数时的租金上限；
  · `above_ceiling_at_target` / `above_ceiling_at_breakeven`：当前租金比这两个上限高多少，**正数 = 需要压的幅度，负数 = 仍有余量**。
  ⚠️ 两个上限都可能为负：负值不是算错，是结论——说明即便零租金也达不到该口径，问题在营收或投入，不在租金。**原样呈现，不得归零。**
- **租期现金流（本版新增，`lease_model`）**：传 `area_sqm` 与 `lease`（`term_years` / `rent_escalation_pct` / `renovation_cycle_years` / `renovation_cost`），把静态回本扩展成合同期内的现金流：
  · 租金按年递增复利，翻新按周期在年末一次性扣除；
  · 输出租期内回本月序、累计付租、累计翻新、期末累计现金，判定 `healthy / tight / fail`；
  · **租期必须与面积匹配**：≥1000㎡ 建议 ≥7 年（长租才能摊薄重装修，3 年合同摊不平），300~1000㎡ ≥5 年，小店 2~3 年。租期短于下限时 `term_warning` 会直接给出警告；
  · **目标回本周期由业态决定，不由租期决定**：茶饮/咖啡约 12 个月，全天茶楼约 27（24~30），大型正餐约 36，中型正餐约 24，便利店约 18。**租期长不代表可以慢回本——回本慢就是少赚钱**，合同长只是「给得起这个时间」。
  · **租期只负责容纳**：合同至少要长到「回本 + 等长的赚钱期」，即 `required_term_years = 目标回本 × 2 ÷ 12`（回本 27 个月的茶楼至少要 4.5 年）。租期不足时 `term_capacity_warning` 给出警告，含义是「刚回本就要续约，赚不到钱」。
  · 调用方显式传 `target_payback_months` 时以其为准，但与业态建议偏离超 25% 会触发 `target_payback_mismatch` 提示，报告须说明是「偏紧」还是「偏松」。
  ⚠️ 静态回本看起来漂亮、但租期内被递增和翻新吃掉的案例很常见——**报财务段必须带上租期现金流，不能只报静态回本**。
- **租售比经验线（按业态，`recommendation`）**：报租金占比时**必须同时给出该业态的健康线与警戒线**，不能只甩一个百分比。经验线：

  | 业态 | 健康线（低于为健康） | 警戒线（高于即超红线） |
  | --- | --- | --- |
  | 茶饮 / 咖啡 | 15% | 20% |
  | 便利店 | 12% | 18% |
  | 快餐 / 粉面 | 12% | 18% |
  | 中型正餐 | 12% | 18% |
  | 全天茶楼 | 10% | 15% |
  | 大型正餐 | 10% | 15% |

  逻辑：大店营业额基数大，租金占比应当更低；小店坪效高，可承受更高占比。行业整体 10%~15% 为健康，>20% 基本难做。
  `rent_ratio_hint` 给出一句话判读（当前值相对两条线的位置与差值），报告须原样引用；**不要只写「偏高」而不给数字**。
- **空间容量与盈亏平衡（`space_model`）**：传 `area_sqm` 与 `space{kitchen_ratio, seat_area_sqm, seats, avg_ticket, daily_customers}`，输出厨房/营业面积、座位数、翻台率、坪效、单方造价、保本营业额（日/月）、保本客单量。
  · **缺面积则整段不计算**，报告写「未计算（原因）」，不得用估算补；缺座位数或客单价时翻台率记 `-1` 并注明缺哪项，**禁止推算**。
  · 三条自动告警：翻台率 < 0.5 次/日（面积过大或营收估低）、坪效低于经验基准 60%（面积利用率低）、容量利用率 > 95%（已到座位上限，再增长只能加面积或提客单）。
  · **翻台率口径（务必分清）**：
    `座翻台 = 日客流 ÷ 座位数`；`桌翻台 = (日客流 ÷ 桌均人数) ÷ 桌数 = 桌次 ÷ 桌数`。
    桌均人数与「座位数÷桌数」一致时两者**数值相同**，别把它们说成差几倍；只有实际每桌坐不满、或给了真实桌数时才分叉。
    业态经验值：全天茶楼 常规 **2.5**／上限 3.5；大型正餐 常规 **2.0**／上限 3.0；中型正餐 2.5／3.5；快餐 4／6；茶饮 6／10。
  · **茶楼 ≠ 正餐，别混**：全天茶楼只喝茶吃点心，没有正餐，客单价 50~110 元、翻台高（2.5+）；
    粤菜酒楼/大型正餐有菜有酒，客单价 150~400 元、翻台低（2.0 左右）。两者产能基准差 25% 以上，**贴错标签整段测算就废了**。
  · **客单价 ↔ 业态标签校验**：`avg_ticket` 落在该业态典型区间外时（例如标签是茶楼但客单 252 元），
    `ticket_matches_format=false` 并给出 `ticket_note`，报告必须原样引用，先让客户确认业态归类再算，不得直接出结论。
  · **输入自洽性校验（必做）**：用 `座位数 × 业态常规翻台 × 客单价` 反推「该面积应有的日营收」，与实际营收假设比。
    - 比值 < 40% → `input_consistency='revenue_too_low'`，报告必须红字写明「面积与营收严重不匹配」，**不要把它当成「翻台率偏低」轻轻带过**；
    - 算出的翻台 > 业态上限 → `turnover_impossible`，说明营收/客单/座位至少有一个是错的；
    - 这两种情况都属于**参数问题**，先让客户核数，别急着往下算财务。
  · 缺省系数（厨房占比、每座面积、桌均人数）必须写进报告，不许静默。
  · **建议翻台率（门槛口径，本版新增）**：翻台率不该只当结果指标，要当门槛指标报。
    `保本翻台率 = 保本日营业额 ÷ 客单价 ÷ 座位数`；
    `目标翻台率 = 目标回本口径日营业额 ÷ 客单价 ÷ 座位数`。
    注意：`日营业额 ÷ 座位数` 只是「元/座/日」，**必须再除以客单价才是翻台次数**。
    `target_within_capacity=false`（目标翻台超过业态上限）意味着这个「面积 × 租金」组合做不出来，必须提示换面积或压租金。
  · **盈亏平衡点日/月是纯派生量**（保本日营业额 × 30），无论空间模型是否算得出来都应报出。
- **拦截**：缺任一参数立刻反问缺哪项。

# 三、 绝对红线
1. **禁止越级**：缺财务参数不算账；无坐标不做空间分析。
2. **禁止写死参数**：必须用传入的 `{gis_radius}`、`{competitor_keywords}`。
3. **禁止幻觉**：距离、数量、份额只能来自 API 返回；缺数时写「数据缺失」，不得用竞品数反推其他指标。
4. **禁止绝对阈值拍档**：任何分级都要说明参照样本与分位口径。
5. **禁止混用坐标系与圈层**：高德 `lng,lat`/`status="1"`；腾讯 `lat,lng`/`status=0`、半径 ≤1000m。
6. **密钥保密**：两把 Key 不得出现在任何输出、报告、日志与新建文件。

## 本地服务与开关（哪些要开、哪些不用开）

三类外部依赖，要求完全不同——**最容易忘的是 Valhalla**。

| 功能 | 本地要开什么 | 忘了会怎样 |
|---|---|---|
| POI 采集 / 财务测算 / 网格扫描 | **什么都不用开**（联网 + 高德 Key） | 无 Key 时采集报缺凭证 |
| 人口栅格核对 | **什么都不用开**（只要装了 QGIS） | 报告写明「人口核对未执行」+ 补齐命令 |
| **等时圈（真实路网）** | **Docker + Valhalla 容器常驻，端口 8002** | 降级为直线估算，报告头部黄色提醒 |

### Valhalla：常忘的那一个

```
# 首次（约 2 GB 镜像 + 瓦片挂载）
docker run -dt --name valhalla -p 8002:8002 -v F:/gis/valhalla:/custom_files ghcr.io/gis-ops/docker-valhalla/valhalla:latest

# 之后（容器已存在）
docker start valhalla

# 不用时释放内存（约 1~2 GB）

```

**判断是否在跑**：`docker ps --filter name=valhalla`
能访问 `http://localhost:8002/status` 返回 200 就是好的。

### 忘了开会怎样（不会静默）

**终端**：

```
⚠️ 等时圈引擎未启用：Valhalla(8002) 与 OSRM(5000) 都不可达
   本次等时圈为【直线估算】——遇江面、快速路、封闭小区会高估可达范围，圈内竞品数偏多。
   首次启动：docker run -dt --name valhalla -p 8002:8002 -v F:/gis/valhalla:/custom_files ghcr.io/gis-ops/docker-valhalla/valhalla:latest
   之后启动：docker start valhalla
   不用时可以 docker stop valhalla 释放内存（约 1~2 GB），下次跑之前记得再 start。
```

**报告头部**（md 与 html 都有黄色提示块）：

```
> ⚠️ 等时圈引擎未启用（Valhalla(8002) 与 OSRM(5000) 都不可达）
> 本次圈层为【直线估算】：直线估算遇江面/快速路会高估可达范围，圈内竞品数偏多。
> 启动：`docker start valhalla`（首次：`docker run -dt ...`）
```

### 直线估算偏差有多大

白鹅潭万象城实测：到芳村站**直线 586m，实测步行 1136m**（1.94 倍）。
隔江、隔快速路、小区封闭的场景，直线估算会把 15 分钟圈画大 1.5~2 倍，**圈内竞品数系统性偏多**。

所以：**要做最终结论前，先把 Valhalla 开起来重跑一次。**


## 人口核对（独立数据源交叉验证）

需求强度来自 POI 代理，测的是**商业活跃度**。常住人口是另一回事——两者对照才能看出商圈性质。

### 它测什么、不测什么

| | WorldPop 人口栅格 | POI 代理强度 |
|---|---|---|
| 测什么 | **常住人口**（晚上谁在这住） | **商务活跃度**（白天谁在这花钱） |
| 来源 | 卫星 + 普查建模，约 93m 栅格 | 高德 POI 密度加权 |
| 精度 | 官方估算，非实测 | 代理指标 |

**单看任何一个都会误判。** 例：CBD 常住人口密度往往低于老城区，但消费力强得多。

### 交叉判定表

| WorldPop 人口 | POI 代理强度 | 判定 | 含义 |
|---|---|---|---|
| 高 | 低 | **机会点** | 人口密集但商业未饱和，优先实地踏勘 |
| 高 | 高 | 成熟商圈 | 两头都强，竞争激烈，拼差异化 |
| 高 | 中 | 居住型商圈 | 社区客为主 |

| 低 | 高 | **泡沫风险** | 商业密集但常住人口少，核实客流来源 |

### 怎么启用（一次性，约 10 分钟）

```bash
# 1) 下载全国栅格（4.7 GB，只需一次）
#    https://data.worldpop.org/GIS/Population/Global_2000_2020/2020/CHN/chn_ppp_2020.tif

# 2) 裁出你的城市（每个 1~8 MB，约 1 秒）
"QGIS安装目录/bin/python-qgis-ltr.bat" scripts/worldpop-clip.py \
    --src "D:/下载/chn_ppp_2020.tif" --city 广州 --outdir data/worldpop

# 3) 自检
"QGIS安装目录/bin/python-qgis-ltr.bat" scripts/worldpop-sample.py \
    --tif data/worldpop/gz_pop_2020_100m.tif --center "23.1035,113.2361"
```

内置 21 个城市：北京 上海 广州 深圳 佛山 东莞 重庆 成都 杭州 武汉 苏州 西安 南京 长沙 天津 青岛 济南 宁波 郑州 合肥 昆明。
其他城市用 `--bbox "minLng,maxLat,maxLng,minLat"` 自己裁。

**依赖**：QGIS（提供 GDAL）。没装 QGIS 时该能力自动跳过，报告会写明原因。

### 未启用时会怎样

报告第 4 段会出现：

```
**人口核对（本次未执行）**
⚠️ 原因：杭州 的人口栅格还没裁
补齐：scripts/worldpop-clip.py --src <WorldPop全国tif> --city 杭州
本次报告缺少独立人口数据源，需求强度全部来自 POI 代理，请按「单源」看待。
```

**降级不静默**——缺哪一环、怎么补，都写在报告里。

### 坐标系必须转

点位是 GCJ-02（高德），栅格是 WGS84。**偏移约 621 米**——500m 半径的圈中心偏 621m，结论全错。
`worldpop-sample.py` 内部自动转换，并在输出里标出偏移量。
